# 律师工作台 3.0 交接件（从零重构）

> **用途**：唯一从 2.0 仓库带进 3.0 新目录的文字。新目录开工后作为 `/wayfinder` 的输入。
> **读法**：第 2、3 节是决定与证据，照读；第 4 节的"处置建议"全是候选，由 wayfinder 逐条裁，不是结论。
> **写于** 2026-09-03，旧仓库冻结在 commit `25c0e37`（插件版本 2.1.4）。
> **红线**：本文件不含任何案件数据；新仓库同样不得含。

---

## 1. 决定

**从零重构，不在 2.0 仓库上改。** 2.0 的规则集（13 条不变量、9 份 ADR、六条"不得改写"的产品原则）已经成为修改的阻力而不是助力，所以整体换掉，而不是逐条修。

**唯一沿用的东西：Matt Pocock 式的 skill 封装形式。** 具体是四件：

1. 仓库初始化（setup 类 skill，一次运行把配置写进目标仓库）；
2. 路由（router：一张全 skill 地图，只提示不触发）；
3. skill 分层：编排层（人手触发、`disable-model-invocation: true`）与参考层（model-invoked、可被其他 skill 调用）；
4. 以插件形态分发 skill 包。

除此之外一切上桌，包括 2.0 的术语表、目录规范、代码、流程。

## 2. 试用发现的问题（这次重构的起因）

按律师实际使用 2.0 的体验记录，每条后面是旧仓库里能核到的佐证。

### 2.1 skill 整合度不够，律师要记的命令太多、反复确认

- 原则上"主循环律师命令不超过两个"（import-archive、draft-document），实际律师面对的是：6 个 user-invoked skill（导入归档、生成文书、审查文书、债权审查、分离空白模板、定流程切分），加 4 个律师动作脚本（批准 / 节点标记 / 分支适用 / 律师陈述），每个动作再分 `--show` 出示与 `--commit` 落盘两段。
- 六条原则的第一条是"自动优先、不做前置逐项确认"，但第二条"批准文书即确认内容"与不变量 2"四项发起权只属律师、两段式执行"把确认又一项项加了回来。两条规则互相抵消，落到使用上就是反复确认。
- 结论：流程没有从律师一天的工作反推，是从"哪些能力要封成 skill"正推出来的。3.0 应先定律师主循环的命令数与确认点，再决定切几个 skill。

### 2.2 可见工作台的呈现形式不符合预期

- 演变路径：网页工作台（需求文档 §10 明写 web 框架）→ ADR-0007 收缩成插件、网页退役 → ADR-0008 改成 Codex 会话内 MCP widget + 落盘 HTML 快照双出口，布局在力导向球形与分层泳道之间来回（ADR-0004、0006）。
- 每一步都是被上一步的技术限制推着走的，没有一步是从"律师想看到什么"出发。
- **律师的期望**：重新设计为官方 MCP 格式，或 app 形式。这是 3.0 的第一道决策题，在动任何 skill 之前裁。

### 2.3 代码机制限制了文书生成的灵活性

- 2.0 的文书写入只有一条通道：模型产"槽位→值"替换清单 JSON，`fill-docx.py` 校验模板指纹后原样写入 DOCX（ADR-0002 把这条 seam 定为不可动）。
- 代价在通用裁定台账里有记录：官方模板的空表格单元格填不了，得给脚本加 `cells` 定址项；长待决标记撑爆窄列；末尾空段落删过头触发 Word 修复提示。每遇一种新版式，就要在脚本里开一个新口子。
- "语义归模型、确定性归代码"这条分界本身不错，但 2.0 把线画得太靠代码侧，模型在文书内容上没有自由度。3.0 从 agent 直接产出文书这一端出发，只在出真实事故时才加确定性脚本。

### 2.4 规则先于证据

- 11 个 skill 配了 13 条不变量、9 份 ADR、六条不得改写的原则，多数写在第一个真实案件之前。
- 不变量 9"每个 skill 在真实工作里用过一次才写下一个"直接禁止整体重构。
- 3.0 候选元规则：一条规则只在真实使用里被违反过一次之后才写进 AGENTS.md。

## 7. 新仓库起步顺序

1. `git init`，只写 §3 两条硬边界进 AGENTS.md，拷入 §5 资产，本文件放 `docs/`。
2. `/setup-matt-pocock-skills` 配 issue tracker 与文档布局。
3. `/wayfinder`，本文件为输入。起手决策票建议（顺序即依赖顺序）：
   - 呈现形态：官方 MCP 格式 / app / 两者，各自对 skill 分发形态的含义；
   - harness 范围：先做哪一侧，另一侧何时接；
   - 律师主循环：一天的工作反推出几个命令、几个确认点，发起权四项的新形态；
   - 文书生成机制：agent 直接产出文书的边界，何种事故才引入确定性脚本；§5 的五种事故形态作为验收项；
   - 案件目录规范与已有案件数据的迁移；
   - 规则元规则：规则如何进入 AGENTS.md。
4. 路清后 `/to-spec` → `/to-tickets` → 逐票 `/implement`，票间 `/clear`。每张 skill 票的完成定义写成"在真实案件会话里被真实触发过一次"。
