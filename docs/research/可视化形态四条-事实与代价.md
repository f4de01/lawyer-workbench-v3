**被事实排除掉的**（排除是事实结论，不是选型）：

1. **官方 MCP App / Plugin UI（第 1 条）今天走不通。** 两处独立的门都关着：Codex 的 `enable_mcp_apps` 仍是未转正的 `false`；Apps SDK 的 `apps` 槽指向服务端注册的 app id，本地摆文件声明不出来。Claude 侧连槽都没有。这不是"代价高"，是"门没开"。
2. **Claude Code 的 `Artifact` 通道对本项目不可用**：它把页面托管到 claude.ai，案件内容要上传，与硬边界 1 同向冲突。

3. **Tauri（第 2 条）不是被排除，但它与既有交付形态正交**：本项目所有分发渠道（skills.sh、两个插件市场、junction、离线兜底包）**没有一条是为分发平台二进制设计的**，而 Tauri 必须分发二进制；macOS 那半还要么付 Apple $99/年、要么接受 Apple Silicon 上「从网上下载的 app 一律要求签名」这条硬拦。这是**代价**，不是关着的门：所以它留在桌上。

**没有被排除、代价已经量出来的**：第 3 条（落盘静态 HTML）依赖最少、30 KB 内联毫无压力，且 Codex 侧还多一条官方内联渲染通道可以叠加；第 4 条（常驻服务）能跑，但 B 节六条代价一条不少，其中「Windows cwd 锁住目录会卡死升级」是本次新发现、候选方案没提。

**票里没列、但必须一起上桌的第五条**：**Codex 自带 `visualize` 插件的内联 HTML 通道**（A.2）。它不装东西、不起常驻进程、不开浏览器，限制（内联、无 `fetch`、1 MB 内）与 `file://` 那条**完全同形**；代价是只在 Codex 一侧、且推断只在桌面应用里可见。**#127 选型时漏掉它，比较就是缺项的。**

## A. 重核「两个 CLI 都还不渲染」

### A.0 旧事实的原文

`docs/research/skill-platforms-claude-code-与-codex.md`（2026-09-04，issue #11）结论速览最后一行：

| 问题 | Claude Code | Codex |
| --- | --- | --- |
| 会话内渲染 MCP App UI | 不渲染（不在官方宿主矩阵；MCP 文档无 UI 条目） | 默认不渲染（`EnableMcpApps` 特性旗标默认 false） |

ADR-0011 据以写下「引擎不出 HTML、不加读视图 CLI、不设 MCP server」，理由是「落盘文件是唯一可见通道」。

这条旧事实有两半，**重核之后一半仍成立、一半被推翻**。

### A.1 仍成立的一半：MCP App UI 两个宿主都不渲染

- **Codex**：`codex features list` 在本机今天的输出里，`enable_mcp_apps` 的 stage 是 `under development`、生效值 `false`。同一张表里 `apps` 是 `stable true`、`terminal_visualization_instructions` 是 `under development false`。**［源码事实］**（本机 `codex features list`，2026-09-12）
- 也就是说 #11 查到的那条「`EnableMcpApps` 默认 false」**一字未变**地仍然成立，九天里没有转正。**［源码事实］**

### A.2 被推翻的一半：Codex 已经有一条官方的富渲染通道，而且不是 MCP

本机 Codex 自带（bundled）一件官方插件 `visualize@openai-bundled`，版本 1.0.37，`enabled = true`。**［源码事实］**

- 清单 `.codex-plugin/plugin.json` 自述：`"description": "Create interactive charts, maps, diagrams, simulations, 3D models, data explorers, and UI previews directly in Codex."`，`capabilities: ["Interactive","Read","Write"]`。**［源码事实］**
- 机制不是 MCP，是**回复正文里的一行内容引用**。它的 `SKILL.md`「Inline HTML output contract」规定：模型把一个 **HTML 片段**（`no <!doctype>, <html>, <head>, <body>`）写成一个 `.html` 文件，然后在最终回复里单起一行写

  ```text
  visualize{"path":"<absolute-path>/<title>.html"}
  ```

  宿主就在对话里把它渲染出来；加 `"mode":"wide"` 可以撑到 1,024px 的可展开内联面。**［源码事实］**
- 渲染是**沙箱 iframe**：随包的 `scripts/render.py` 把片段包进 `<iframe sandbox="allow-scripts" srcdoc=...>`，外层与内层各一份 CSP。内层 CSP 明文 `default-src 'none'`、`connect-src blob: data:`。**［源码事实］**
- 因此有两条硬限制，白纸黑字写在 `SKILL.md` 里：**「Never use `fetch`, XHR, WebSocket, or other API calls.」**、**「Keep visualizations under 1 MB.」**。数据只能内联进片段。**［源码事实］**
- 外部资源只许从白名单 CDN 取（`render.py` 里的 `_RESOURCE_SOURCES`）：`cdnjs.cloudflare.com`、`cdn.jsdelivr.net`、`esm.sh`、`unpkg.com`、`fonts.bunny.net`、`fonts.googleapis.com`、`fonts.gstatic.com`，外加 `blob:` 与 `data:`。**［源码事实］** 对一张只画本地 JSON 的图来说，这条限制等于不存在：**零外部依赖就能画**。**［设计推断］**
- 同一个 `render.py` 还带 `--serve`：它自己就是用 `ThreadingHTTPServer` 绑 `127.0.0.1`、端口默认 0（让 OS 挑）起一个临时服务供浏览器看的。**［源码事实］** 也就是说，「本地 HTTP 服务 + 浏览器」这条路的**最小形态，官方自己在用**：但它是**给模型自检用的临时进程**（`serve_forever()` 直到 Ctrl-C），不是常驻物。**［源码事实］**
- 协议层面对得上：Codex CLI 二进制里有 `BemItemPresentation` 的枚举变体 `inline_visualization`（与 `whole_item`、`inline_markdown` 并列）。**［源码事实］**（`codex.exe` 字符串）

### A.3 但「在哪个宿主里渲染」要分开算

Codex 的系统提示里有**两套** `### Visualizations` 段落，同在一个二进制里：

- 一套只许 **表格 / 流程 / 时间线 / 树 / 线框**，措辞是「Prefer the smallest useful visual: a table for mappings or comparisons, a flow or timeline for sequence or change, a tree for hierarchy or branching, and a wireframe for layout.」：全是纯文本能画的东西。**［源码事实］**
- 另一套说「**Prefer inline visualizations** for nontechnical planning, schedules, and explanations, or when interaction materially improves understanding.」，并且「For small, static software or engineering diagrams ... prefer Mermaid.」**［源码事实］**

两套并存，加上旗标名叫 `terminal_visualization_instructions`，最合理的读法是：**终端 TUI 走第一套（不渲染 HTML），桌面应用走第二套（内联 HTML）**。**［设计推断］**：没有任何一处官方文字直说「TUI 不渲染 `visualize{}`」，所以这是推断，不是事实。

旁证四条：

- 终端里 Codex 唯一用到图像协议的地方是「terminal pets」，报错文案是「This terminal environment doesn't expose a supported image protocol. Try a terminal with Kitty graphics or Sixel support」「Pets require iTerm2 3.6 or newer」。**［源码事实］**：即 TUI 的图像能力是 Kitty/Sixel 级的位图，不是 HTML 引擎。
- **官方仓库里「TUI 内联显示图片」的两条 issue 至今 open**：`openai/codex#29451`「Show image artifacts inline in the Codex TUI」（建于 2026-06-22）、`#35755`「[TUI][Warp] view_image succeeds but no inline image is rendered」（建于 2026-07-28），**2026-09-12 查仍是 open**。**［源码事实］**（GitHub issue state）：Codex 有 `view_image` 工具，但那是给模型"看"的多模态输入，**不等于终端把图画出来**。
- Codex 的 skill 机制里 `agents/openai.yaml` 的 `interface` 字段，官方原文说的是「configure UI metadata **in the ChatGPT desktop app**」；同一页另写「In Codex, the initial list also includes each skill's file path」：**UI 元数据只喂桌面应用，CLI 侧仍是纯文本清单**。**［源码事实］**
- 本机 `~/.codex/visualizations/` 下按 `年/月/日/<thread-id>/` 存着历次生成的 HTML（最早 2026-07-10，最近 2026-09-13）。**［源码事实］**：说明这条通道在这台机上被真实用过。

把这四条与前面两套 `### Visualizations` 提示词放在一起：**「Codex 终端 TUI 不渲染 HTML、不内联图片」已经从推断逼近事实**；仍留在推断一栏的只剩「`visualize{}` 那一行在 TUI 里具体退化成什么样」：没有一处官方文字说过。**［设计推断］**

**结论 A**：「两个 CLI 都还不渲染」在 2026-09-12 **只对终端 TUI 仍然成立**；对 **Codex 桌面应用**已经不成立：那里有一条官方的、内联的、沙箱 iframe 的 HTML 渲染通道，而且不走 MCP。「落盘文件是唯一可见通道」这句话要改成：**落盘文件仍是唯一的数据落点，但它现在可以被宿主直接渲染，不必再靠律师自己去双击**。

### A.4 Claude Code 这一侧：有渲染通道，但它是托管的

- Claude Code 2.1.270 自带 `Artifact` 工具：把一个本地 `.html` 文件发布成 **claude.ai 上的一个网页**，返回 URL；默认私有；`/artifacts` 列出、`ctrl+]` 打开本会话最近一个；网页端在 `claude.ai/code/artifacts`。**［源码事实］**（本会话工具清单 + `claude.exe` 内文案）
- 官方文档（`code.claude.com/docs/en/artifacts`，2026-09-12）原文：「An artifact is a live, interactive web page that Claude Code publishes from your session to a **private URL on claude.ai**. **You open it in a browser**」；可用性写明「Surface: **Claude Code CLI version 2.1.183 or later**, or the Claude desktop app」；自动开浏览器可用 `CLAUDE_CODE_ARTIFACT_AUTO_OPEN=0` 关掉。官方博客「Artifacts in Claude Code」发布于 **2026-06-18**。**［源码事实］**
- 它**不是本地渲染**：页面内容上传到 Anthropic 的服务器、由浏览器打开那个 claude.ai 链接才看得见。**［源码事实］**
- 同源的 `/design` canvas（要求 CLI v2.1.234+）也是「发布成 artifact 再由浏览器渲染」，不是终端内渲染。**［源码事实］**
- **对本项目这等于不可用**：把案件图视图发布成 claude.ai 上的网页，直接撞 `AGENTS.md` 硬边界 1（案件材料只存在于本机案件工作区）。**［设计推断］**：硬边界 1 管的是"不入本仓库"与"不进 issue"，把案件内容上传到第三方托管页面是不是同一条禁令，文本上没写死，但方向上显然同源。这一条要请认领人拍。
- **Claude Code 的终端本身不渲染 HTML，也不渲染图像。［源码事实］** 三条证据：(1) 官方仓库 issue `anthropics/claude-code#2266`「Feature Request: Terminal Graphics Protocol Support (Sixel, Kitty, iTerm2)」建于 2025-06-18、2026-04-07 以 `completed` 关闭，但评论里用户明问「Completed? we cannot render pictures inline on terminal?」：**属清理式关闭，功能没落地**（重复票 `#29254` 同样）；(2) 官方 Chrome 集成文档写明截图只能 `save to disk`、不内联显示；(3) 在 `claude.exe` 里检索 `sixel` 零命中，`kitty` / `iTerm` 的命中全是终端分屏与键盘协议。**［源码事实］**
- **Claude Code 官方 MCP 文档（`code.claude.com/docs/en/mcp`）全文没有 `ui://`、iframe、webview、MCP Apps 任何字样。** 也就是说「Claude Code CLI 支持 MCP UI resource」这件事，在 Anthropic 一手来源里**查不到**任何支持证据。**［查不到］**：第三方转述里那个"支持名单含 Claude"指的多半是 claude.ai / 桌面应用的聊天界面，不能记到 Claude Code CLI 头上。
- 另一条别混的：**IDE 扩展（VS Code / JetBrains）与终端 CLI 是两条不同的渲染管线**，前者有编辑器原生面板（inline diff、会话列表、模型下拉），不能拿它当 CLI 的能力。**［源码事实 + 设计推断］**

### A.5 Codex 还自带一个能开 `file://` 与 `localhost` 的应用内浏览器

`browser@openai-bundled`（26.908.40834，`enabled = true`）的清单里，`description` 原文：

> Use Browser, the ChatGPT in-app browser, when the user asks to open, inspect, navigate, test, click, type, or screenshot local web targets such as **localhost, 127.0.0.1, ::1, file:// URLs**, or the current in-app browser tab.

**［源码事实］**（本机 `~/.codex/plugins/cache/openai-bundled/browser/*/.codex-plugin/plugin.json`）

这对第 3、第 4 条形态都是直接相关的事实：**落盘的 HTML 与本地 HTTP 服务，在 Codex 这一侧都有一个官方的、模型能自己驱动的打开方式**，不必只靠律师去双击文件。它是给模型用的自动化浏览器（导航、点击、截屏），**不等于给律师看的常驻窗口**：两者别混。**［设计推断］**

同一份清单还给出了「常驻物怎么收尾」的官方范例：它用 `Stop` / `SubagentStop` / `Interrupt` 三个 hook 事件调 MCP 工具 `turn_ended`。**［源码事实］** 详见 B.2。

### A.6 要画的数据有多大：30 KB 量级

实测（2026-09-12，本机）：`python scripts/skill-eval.py --materialize 在办中` 摊开一个「已办了几步」的合成工作区，破产领域整份起手、12 个模块 72 个节点、两份文书、两条律师陈述：

| 文件 | 字节 |
| --- | --- |
| `图.json` | 17,611 |
| `图视图.json` | 30,325 |
| `图视图.md` | 13,899 |

`图视图.json` 顶层键：`格式版本`（值 1）、`领域`、`生成时间`、`源图`、`模块`、`前方`。**［源码事实 / 本机实测］**

**这个数量级很要紧**：30 KB 远在 Codex `visualize` 通道 1 MB 的片段上限之内，也远在「整个内联进一个 HTML」这条路的舒适区里。**换句话说，「必须内联、不许 `fetch`」这条限制在本项目的数据规模下不构成障碍。［设计推断］**（一个真实案件的条目数比合成种子多多少，本次没有数据，**［查不到］**；但即便乘 10 也只有 300 KB。）

### A.7 `file://` 下能做什么、不能做什么（本机实测）

第 3 条形态成败的那条限制，本次直接测了，不靠文档转述。

测法：同目录三件 ： `page.html`、`data.json`、`mod.js`；页面里依次试 ESM 动态 `import`、`fetch`、同步 `XMLHttpRequest`、`localStorage`；用 `--headless=new --dump-dom` 跑，读回 DOM。

| 能力 | Chrome 152.0.7977.84 | Edge 153.0.4234.32 |
| --- | --- | --- |
| `import("./mod.js")` | **FAIL** `TypeError: Failed to fetch dynamically imported module` | **FAIL** 同上 |
| `fetch("./data.json")` | **FAIL** `TypeError: Failed to fetch` | **FAIL** 同上 |
| `XMLHttpRequest` 同步取同目录 JSON | **FAIL** `NetworkError` | **FAIL** 同上 |
| `localStorage` 读写 | **OK**，且 `location.origin === "file://"` | **OK**，同 |

**［源码事实 / 本机实测］**（2026-09-12）

三条结论：

1. **`file://` 下数据必须内联进 HTML**，不能旁挂 `.json`、也不能拆 ES module。这与 A.2 那条通道的限制**完全一致**：两条路对「数据怎么进页面」提的是同一个要求，30 KB 的体量（A.6）让它不成问题。**［设计推断］**
2. **所有 `file://` 页面共享同一个 origin（`"file://"`）**，`localStorage` 因此在不同案件、不同页面之间是**混用的**。要按案件存界面偏好，得自己在 key 里带工作区标识。**［源码事实 / 本机实测］**
3. **Safari 没测。** 律师那台是 mac，默认浏览器很可能是 Safari，它的 `file://` 策略与 Chromium 历来不同。**［须实测］**

## B. 常驻进程的四条事实

体系现状：所有 CLI 都是跑完就退，没有任何常驻物（`skills/*/scripts/*.py` 全是一次性子进程）。第 4 条形态的成败全在这四条上。本节的实测全在 **Windows 11** 上做；**macOS 一条都没测**。

### B.1 模型回合结束后进程还在不在

**在。［源码事实 / 本机实测］**

实测（2026-09-12，本机）：用 `subprocess.Popen` 起四个 `http.server.ThreadingHTTPServer`（绑 `127.0.0.1`、端口 0），四种 creationflags 组合各一个：

| 组合 | 起得来 | 起它的进程退出后 |
| --- | --- | --- |
| 无 flags | 是 | 活着，HTTP 200 |
| `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP` | 是 | 活着，HTTP 200 |
| 再加 `CREATE_BREAKAWAY_FROM_JOB` | 是 | 活着，HTTP 200 |
| `pythonw.exe` + `DETACHED_PROCESS` | 是 | 活着，HTTP 200 |

四个的父进程（那个起它们的 python）已经 `alive=False`，四个全成了孤儿，仍在服务。Windows 不回收孤儿进程。**［源码事实 / 本机实测］**

### B.2 宿主退出后怎么办、谁负责清理旧实例

**两个宿主的非交互进程退出后，服务都还活着。［源码事实 / 本机实测］**

这一条我做了端到端实测，不是推断：

- **Claude Code**：`claude -p "<起一个服务>" --allowedTools Bash --max-turns 6` 跑完退出（退出码 0）。它起的服务 PID 在宿主退出后仍 `ALIVE`，`http://127.0.0.1:<port>/` 仍返回 200，父进程已 `alive=False`。**［源码事实 / 本机实测］**
- **Codex**：`codex exec --cd <dir> --skip-git-repo-check -` 跑完退出。同样：服务仍 `ALIVE`、HTTP 200、父进程已 gone。**［源码事实 / 本机实测］**

两条附带事实：

- **Codex 沙箱的 PATH 不含 `python`**。第一次实测里 `python spawn_one.py` 直接 `CommandNotFoundException`，换成解释器绝对路径才跑通；Codex 把命令包在 `powershell.exe -Command` 里执行（`sandbox_mode = "workspace-write"`、`[windows] sandbox = "elevated"`）。**［源码事实 / 本机实测］**：随包脚本若要从 Codex 会话里起服务，不能指望 `python` 在 PATH 上。
- **作业对象（Job Object）这条坑在这台机上没踩到，但机制在**。本机 PowerShell 宿主进程自身 `IsProcessInJob = True`，其 job 的 `LimitFlags = 0x800`，即 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 置位；而由它起的子 python 报 `IsProcessInJob = False`，并且 `CREATE_BREAKAWAY_FROM_JOB` 起进程**没有**失败。**［源码事实 / 本机实测］** 也就是说：**这台机上的子进程没有被关进那个 kill-on-close 的 job**，所以活了下来。但这是这台机、这个版本、这条调用路径的结果，**不是平台保证**：换个终端宿主（有些终端会把整棵树关进带 `KILL_ON_JOB_CLOSE` 的 job）结果就可能相反。**［须实测］**：律师那台 mac 与她实际用的终端上各测一次。

**谁清理**：现在**没有人清理**。两个宿主都给了机制，但都要自己接上：

- **Codex 的 hook 事件**（`codex.exe` 里的枚举）：`PreToolUse`、`PermissionRequest`、`PostToolUse`、`PreCompact`、`PostCompact`、`SessionStart`、**`SessionEnd`**、`UserPromptSubmit`、`SubagentStart`、`SubagentStop`、`Stop`、`Interrupt`。**［源码事实］** 官方 `browser@openai-bundled` 插件正是用 `Stop` / `SubagentStop` / `Interrupt` 三个事件调一个 MCP 工具 `turn_ended` 来收尾的：**官方自己就是这么清理常驻物的**。**［源码事实］**（该插件的 `.codex-plugin/plugin.json`）
- **Claude Code 的 hook 事件**：`SessionStart`、`SessionEnd`、`PreToolUse`、`PostToolUse`、`UserPromptSubmit`、`Stop`、`SubagentStop`、`PreCompact`、`Notification`。**［源码事实］**（`claude.exe`）
- 代价：hook 要进 `plugin.json`，而本仓库两份 plugin.json 现在都只有 `skills` 一项。加 hook 等于给两个平台各写一份、各走一遍 `docs/agents/skills.md` 的登记八步。**［设计推断］**
- 另一条不依赖宿主的手艺：**超时自杀**（N 秒没收到请求就退）+ PID 文件/端口探测复用。标准库做得到，与宿主无关。**［设计推断］**

### B.3 双平台后台启动：Windows 不弹窗、macOS 的启动与退出

- **Windows 不弹多余终端窗口：做得到。［源码事实 / 本机实测］** 上表第 4 行用 `pythonw.exe` + `DETACHED_PROCESS` 起服务，没有控制台窗口，服务正常。`python.exe` + `DETACHED_PROCESS` 也没弹窗（`DETACHED_PROCESS` 的定义就是不继承也不新建控制台）。
- **macOS 的启动与退出：一条都没测。［须实测］** 本次没有 mac。要测的至少三件：孤儿进程被 launchd 收养后是否照常服务；终端窗口关闭时 SIGHUP 沿进程组传播会不会带走它（要不要 `os.setsid()`）；`open` 命令拉起浏览器的行为。
- 律师那台 mac 的 `/usr/bin/python3` 是 3.9.6（`docs/agents/skills.md` 记的 #61），随包脚本本来就按 3.9 写，`ThreadingHTTPServer` 3.7 就有，够用。**［源码事实］**

### B.4 包更新之后，旧进程仍持着旧代码，怎么生效

**不会自己生效，必须重启进程。而且在 Windows 上它还会把安装器挡住。［源码事实 / 本机实测］**

实测一：起一个服务，回显 `import` 来的 `lib.VERSION`。原子替换 `lib.py`（`v1` → `v2`）并删掉 `__pycache__` 之后：

- 跑着的服务仍回 `v1`；
- 新起一个进程读到 `v2`。

即 Python 的模块缓存（`sys.modules`）意味着**换盘上的 .py 对已跑的进程零影响**。**［源码事实 / 本机实测］**

实测二（更要命的一条，本次新发现）：那个服务的**工作目录**在被替换的目录里。趁它跑着：

- `Rename-Item` 该目录：**失败**，「The process cannot access the file because it is being used by another process.」
- `Remove-Item -Recurse -Force`：**同样失败**。
- 杀掉进程之后，删除立刻成功。

**［源码事实 / 本机实测］** 结论：Windows 锁住进程的 cwd。**一个把 cwd 留在 skill 目录里的常驻服务，会让「替换整个 skill 目录」这种安装/升级动作直接失败**。躲法很便宜（启动后 `os.chdir()` 到别处、或用绝对路径起进程且不设 cwd），但**必须写进设计，不能靠运气**。**［设计推断］**

### C.1 skills.sh（`npx skills@latest add owner/repo`）

### C.2 Claude 插件市场安装

**复制的是整个仓库，包括与 skill 无关的东西。［源码事实 / 本机实测］**

- `installed_plugins.json` 逐条记 `installPath`、`version`、`gitCommitSha`；更新是换一个版本目录。**［源码事实］**

`.codex-plugin/plugin.json` 的 `skills` 是单一路径 `./skills/`（递归扫描）。Codex 原生的市场清单文件叫 `.agents/plugins/marketplace.json`（本机 `~/.agents/plugins/marketplace.json` 的实际形状：`name` + `interface.displayName` + `plugins[]`，每条带 `source`、`policy`、`category`）。**［源码事实］**

### C.4 开发用目录联接（junction）

`scripts/link-skills.ps1` 把 `skills/<name>/` 逐条 junction 到 `~/.claude/skills/` 与 `~/.agents/skills/`。本机现状：两个目录下七件 loo0ng skill 全是指向本仓库的 Junction。**［源码事实 / 本机实测］**

### C.5 离线兜底包（`scripts/pack-offline.py`）

按 `.claude-plugin/plugin.json` 的 `skills` 数组拷整个 skill 目录，排除 `__pycache__`、`.git`、`.DS_Store`、`.pyc`。**［源码事实］**

**安装源必须是公开仓库。** 私有仓库在律师那台 mac 上一条安装路都没走通，本仓库为此转成 public（#94，2026-09-09 现场；`docs/agents/skills.md`）。**［源码事实］** 这条对可视化资源同样有效：**页面与脚本会随公开仓库公开**，所以里面一个字节的案件内容都不能有：这与硬边界 1 同向，不冲突。**［设计推断］**

- **content type 只有五种**：`ContentBlock = TextContent | ImageContent | AudioContent | ResourceLink | EmbeddedResource`，`type` 字面量 `text|image|audio|resource_link|resource`。**HTML 不是一等类型**，只能借 `EmbeddedResource.mimeType`（无枚举约束）间接携带。**［源码事实］**
- **官方扩展 SEP-1865「MCP Apps: Interactive User Interfaces for MCP」状态是 Final（Extensions Track）**，PR #1865 于 `2026-01-28` 合入，落盘为 `seps/1865-...md`（`Status: Final`、`Type: Extensions Track`、`Created: 2025-11-21`），完整规范另在官方独立仓库 `github.com/modelcontextprotocol/ext-apps`。**［源码事实］**
- 关键分辨：这个 Final 是**扩展轨道**的终态，**不等于并入核心协议**：与上面 schema 检索零命中互相印证。治理规则来自另一条 Final 的 SEP-2133「Extensions」（官方扩展统一 `ext-` 前缀、挂 modelcontextprotocol org）。**［源码事实］**
- 该扩展为 HTML 定了专属 MIME：`text/html;profile=mcp-app`。**［源码事实］**
- **`mcp-ui` 不是官方项目**：`idosal/mcp-ui` 归属组织是 `MCP-UI-Org`，不是 `modelcontextprotocol`。SEP-1865 官方原文把它定性为「community playground for the UI spec and SDK」，并说「The architecture of both the Apps SDK and MCP-UI has significantly informed the design of this specification.」**［源码事实］**

### D.6 OpenAI Apps SDK：建在 MCP 之上，声称跨宿主，但登记在服务端

- **文档路径已迁移**：`developers.openai.com/apps-sdk/*` 现 301/308 永久跳到 `developers.openai.com/plugins/*`。OpenAI 把原来独立的 "Apps SDK" 文档并进了新的 **Plugins** 体系（一个 plugin = skills + MCP server + 可选 UI）。**［源码事实］**
- **与 MCP 的关系**：help.openai.com 原文「It is built on the Model Context Protocol (MCP)... The Apps SDK **extends** MCP so apps built with it can run anywhere that adopts the standard.」**［源码事实］**
- **四种呈现形态**：Inline card、Inline carousel、Fullscreen、Picture-in-picture。**不是在 tool 定义里静态声明的**，而是运行时由组件调 `window.openai.requestDisplayMode({ mode })` 请求、**宿主决定批不批**。**［源码事实］**
- **字段现状**：标准键是 `_meta.ui.resourceUri`（指向承载组件 HTML 的 MCP resource，URI 形如 `ui://…`）；`openai/outputTemplate` 已被官方降级为**兼容别名**（原文：「MCP Apps standard: `_meta.ui.resourceUri`. ChatGPT compatibility alias: `_meta["openai/outputTemplate"]`.」）。同批别名还有 `openai/widgetAccessible`、`openai/widgetCSP`、`openai/widgetDomain` 等。**［源码事实］**
- **`text/html+skybridge` 已从文档里消失**（全文检索零命中），但在官方示例仓库 `openai/openai-apps-sdk-examples` 的代码里仍在（该仓库最后 push 2026-04-15）：文档已更新、示例未跟进。**［源码事实］**
- **宿主限制这一问**：官方措辞把 ChatGPT 说成该开放标准的**一个实现者**（「ChatGPT implements the open MCP Apps standard」「lets the same UI run in ChatGPT and other compatible MCP Apps hosts」），同时反复叮嘱「Keep tools useful **without** UI so the model can complete the workflow in clients that do not render components.」：**官方承认存在不渲染 UI 的 client，但没有点名任何具体产品。［源码事实］** 因此「Codex 桌面/终端会不会渲染」**不能从这份文档外推**，只能看 Codex 自己的旗标（A.1：`enable_mcp_apps` 仍 false）。**［设计推断］**
- **2023 年那套 `ai-plugin.json` 插件早已废弃**：官方「Winding down the ChatGPT plugins beta」页现网 404，Wayback 2024-02-27 快照原文「The creation of new conversations with plugins will be disabled on March 19, 2024... continue existing plugin conversations until April 9, 2024.」接棒的是 custom GPTs；而 custom GPTs 现在**也在被弃用**，官方当前文章（约 2026-09-11 更新）称计划退役、建议迁往 Plugins，企业工作区退役日期定在 2026-12-11。**［源码事实］** ：三代同名不同物，写文档时别混。

### D.8 vercel-labs/skills（`skills.sh` 的那个 CLI）

## E. 逐条答候选方案第 14 节的七个问题

候选方案（`loo0ng案件便签-呈现与分发方案调研-供Claude评估.md`，2026-09-12，Codex 会话产，在本仓库之外）第 14 节留下七问。它自陈未跑过图引擎、未建原型、未实测任何分发渠道与进程生命周期。**它推的第 4 条不享有默认胜出**，下面逐条答，**只给事实，不选型**。

### E1　本地网页 + Python 服务是不是当前交付约束下最小且可维护的方案？有没有更少依赖的替代路径？

**有更少依赖的路径，而且不止一条。［源码事实］**

- 「本地网页 + Python 服务」的依赖是：一个常驻进程 + 一个浏览器 + 一套进程生命周期治理（B 节四条，其中至少三条还没解）。
- 「落盘静态 HTML」的依赖是：一个文件。数据 30 KB（A.6），内联进去毫无压力；`file://` 下不许 `fetch` 这条限制因此不咬人。
- 「Codex `visualize` 内联通道」的依赖是零：不装东西、不起进程、不开浏览器，写一个 HTML 片段落盘 + 回复里一行 `visualize{"path":...}`（A.2）。片段上限 1 MB，本项目 30 KB。

所以「最小」这顶帽子，按本次查到的事实**戴不到第 4 条头上**。第 4 条换来的是「自动刷新」与「长驻窗口」，那是不是需求，是 #127 的事，本票不判。

### E2　展示能力该是独立 skill、现有入口的附属能力，还是包内独立组件？

**本票不答。** 这一问就是地图 6 号票（「接通插件的那件 skill 存不存在」）的题面，而且 ADR-0011 关掉「图存档」skill 槽的理由要在那里被正面回答。本票只提供它需要的事实：

- A.2 那条通道**不需要任何新入口**：它是模型在回复里写一行内容引用，触发条件是「模型判断该画」。**［源码事实］**
- 第 4 条需要一个入口（谁去 start / stop 那个进程）。**［设计推断］**
- 第 1、2 条各自的入口形态见 D、F。

### E3　实际 GitHub 安装与更新渠道会复制哪些内容？建议目录是否可完整分发？

**答案在 C 节，逐条是：**

| 渠道 | 复制范围 | `skills/<name>/assets/` 到不到 |
| --- | --- | --- |
| skills.sh | 整个 skill 文件夹（`scripts/` 实测带到） | 到（**［设计推断］**，见 C.1 的 ［须实测］） |
| Claude 插件市场 | **整仓克隆**，连 `.git`、`.changeset` 都在 | 到 |
| Codex 插件市场 | 同上（读 `.claude-plugin/marketplace.json`，实测通） | 到 |

**候选方案 §7.1 的建议目录（`skills/loo0ng-view/{SKILL.md,scripts/serve.py,assets/*}`）在五条渠道上都能完整到达。［设计推断］** 反过来，**放在仓库根目录的应用目录只有插件市场那两条能带到，skills.sh 与离线包都不带。［源码事实］**

### E4　服务生命周期、重复启动、旧版本进程和双平台路径处理，是否会抵消轻量分发的收益？

**事实摆在 B 节，收益抵不抵得消是 #127 的判断，本票不判。** 能钉住的是代价清单：

1. 进程**不会**自己消失（B.1、B.2 双平台实测）。
2. 没有任何一方在清理（B.2）。两个宿主都有 `SessionEnd` / `Stop` hook 可接，但要各写一份进 plugin.json，并各走一遍登记八步。
3. 旧代码**不会**热生效，必须重启（B.4 实测一）。
4. Windows 上跑着的服务会**挡住**替换 skill 目录（B.4 实测二）：这一条是本次新发现，候选方案没提。
5. Codex 沙箱的 PATH 里**没有** `python`（B.2）：随包脚本要自带解释器发现逻辑。
6. macOS 侧**一条都没测**（B.3）。

### E5　现有视图接口能否支持首版全部展示？领域更新与视图新鲜度选什么口径？

**接口形状与体量是事实，够不够画是 5 号票（「插件读什么，谁给它」）的题面，本票不判。** 事实：`图视图.json` 顶层 `格式版本 / 领域 / 生成时间 / 源图 / 模块 / 前方`，合成种子实测 30,325 字节、12 模块 72 节点、`格式版本: 1`（A.6）。**［源码事实］**

新鲜度：ADR-0011 定的是「引擎每次写图之后覆盖重算」，**没有**任何「领域活图变了就重算案件视图」的触发器。**［源码事实］**（ADR-0011 正文）候选方案 §12.1 把这一条识别对了。

### E6　前方、状态计数、模块完成、时限的呈现是否严格保持现有业务语义？

**本票不答。** 这是呈现语义题，属于「界面的具体设计与首版范围」，地图 #122 的 Out of scope 明文另行单独进行。事实只有一条：状态推算规则住引擎（ADR-0003、ADR-0011），**插件不得复刻**。**［源码事实］**

### E7　哪些明确的用户需求出现后，才值得引入 Tauri 或宿主内 MCP UI？

**这是选型判据题，是 #127 的事。** 本票只钉三条事实：

- **宿主内 MCP UI**：`enable_mcp_apps` 在 codex-cli 0.154.0 仍是 `under development / false`（A.1）；Apps SDK 的 `apps` 槽指向的是**服务端注册的 app id**（D.2）。**两条合起来说明：这条路今天不是"做不做"的问题，是"还没开门"。［设计推断］**
- **Tauri**：见 F 表与 G 节，代价集中在构建链、签名公证与更新链路，与"随 skill 包分发一个纯文件包"这个既有交付形态正交。
- **一条候选方案完全没提的事实**：Codex 桌面应用已经有一条官方内联 HTML 通道（A.2），它既不是 MCP UI 也不是 Tauri，也不需要常驻进程。**任何"什么时候才值得上 Tauri / MCP UI"的判断，都必须把这条一起放进去比。［设计推断］**

- 通用：Rust（`rustup`）；Node.js **只在**用 JS 前端框架时才要（原文「Only if you intend to use a JavaScript frontend framework」）。**［源码事实］**
- Windows：原文「Tauri uses the Microsoft C++ Build Tools for development as well as Microsoft Edge WebView2. These are both required for development on Windows.」：要装 C++ Build Tools（勾 Desktop development with C++）。**［源码事实］**
- macOS：只做桌面可只装 **Xcode Command Line Tools**（`xcode-select --install`）；开发机要求 macOS Catalina (10.15) 及以上。**［源码事实］**
- **→ 律师那台没有开发工具链的 mac 不可能本机构建。构建必须在开发者机器上做。［设计推断］**

**运行期依赖**

- Windows：原文「WebView 2 is already installed on Windows 10 (from version 1803 onward) and later versions of Windows.」：**Win11 自带，零安装**。**［源码事实］**
- macOS：WKWebView 系统自带（Process Model 页「WKWebView on macOS」）；打出来的 app 默认 `minimumSystemVersion` 是 `10.13`。**［源码事实］**
- WebView2 的四种打包策略（Windows Installer 页，Last updated 2026-09-03）：`downloadBootstrapper`（默认，需联网，+0 MB）、`embedBootstrapper`（+约 1.8 MB）、`offlineInstaller`（+约 127 MB）、`fixedVersion`（+约 180 MB）、`skip`（官方标「⚠️ Not recommended」）。**［源码事实］**

**体积**

- 官方首页唯一的数字：「the size of a Tauri app can be little as **600KB**」。**［源码事实］**
- 按平台细分的实际 `.msi` / `.dmg` 字节数官方**没给**。**［查不到］**

**签名与公证**（macOS 页 Last updated 2026-05-17；Windows 页 2026-09-11）

- macOS 原文：「Code signing is required on macOS to allow your application to be listed in the Apple App Store **and to prevent a warning that your application is broken and can not be started, when downloaded from the browser**.」**［源码事实］**
- macOS 原文：「Code signing on macOS requires an Apple Developer account which is either paid (**99$ per year**) or on the free plan (only for testing and development purposes). You also need an Apple device where you perform the code signing.」免费账号「you will not be able to notarize your application and it will still show up as **not verified**」。**［源码事实］**
- Ad-hoc 签名（`"signingIdentity": "-"`）可用，但官方警告它「does not prevent MacOS from requiring users to **whitelist the installation in their Privacy & Security settings**」，并说明「on ARM (Apple Silicon) devices, **code-signing is required for all apps from the Internet**」。**［源码事实］**
- Windows 原文：「**It is not required to execute your application on Windows, as long as your end user is okay with ignoring the SmartScreen warning or your user does not download via the browser.**」：**Windows 侧宽松得多**。**［源码事实］**

**跨平台交叉编译**

- **官方站上没有交叉编译专页**（对 sitemap 全量 URL 做关键词检索，无 `cross-compil` 页面）。**［查不到］**
- 能拼出的官方口径：macOS 的 Application Bundle 与 DMG 两篇分发指南都写「you can use the Tauri CLI and run the `tauri build` command **in a Mac computer**」。**［源码事实］**
- 反方向可行：Windows 签名页写「When cross compiling Windows installers **from Linux and macOS machines**, you must use a custom sign command…」：官方认可"从 Linux/macOS 出 Windows 安装包"。**［源码事实］**
- 从 Windows 出 macOS 产物只在 `wry` README 的故障排查里提过一句（用第三方 `osxcross`，且会撞 `Class with name WKWebViewConfiguration could not be found`，要手加 `RUSTFLAGS="-l framework=WebKit"`）。**这不是官方支持的路。［设计推断］**

**能不能只做「打开一个本地 HTML」的轻量壳**

- **不能免编译。［源码事实 + 设计推断］** Tauri 本体没有轻量模式，任何 app 都要 `cargo tauri build` 出一个自带 Rust 二进制的可执行文件；官方也**没有**提供一个"点一下就能打开任意本地 HTML"的预编译通用产物。**［查不到］**
- 更底层的 `wry`（Tauri 团队自己维护）几十行 Rust 就能起一个指向任意 URL（含 `file://`）的 webview 窗口，但**仍要写 Rust、仍要 `cargo` 编译出平台二进制**。**［源码事实］**

**进程模型与 sidecar**

- Tauri 是多进程：一个 **Core 进程**（Rust，唯一有完整系统权限，管窗口与 IPC）＋ 一个或多个 **WebView 进程**。**Core 进程本身就是常驻物**（窗口存续期间在，全部窗口关掉即退，除非另配托盘）。**［源码事实］**
- **sidecar** 是另一回事：`bundle.externalBin` 声明外部可执行文件（文件名要带 `-$TARGET_TRIPLE`），打进安装包，运行时由 Core 进程经 `shell` 插件拉起，并要在 capabilities 里显式授权 `shell:allow-execute` / `shell:allow-spawn`。**关系是 Tauri app 当爹、sidecar 当儿子**，不是反过来。**［源码事实］**

**有没有「给一个 CLI 工具挂个可选查看器」的官方用法指引**

- **查不到。** 官方 Distribute 分类下全是"如何分发一个完整独立 app"的视角（App Store / DMG / macOS Application Bundle / Microsoft Store / Windows Installer / Flathub / Snapcraft…），没有这种场景化指南；也没有一句官方原文写「必须随主程序一起分发二进制」：那是从上面的架构事实推出来的。**［查不到 + 设计推断］**

**对本项目的直接含义（标推断）**

引入 Tauri 等于在「纯文件、随 skill 包分发、零第三方依赖」这条既有交付形态之外，另开一条**平台二进制**的交付线：开发者要在 mac 与 Windows 各构建一次（mac 那次只能在 mac 上做），要么付 Apple $99/年签名公证、要么接受 Apple Silicon 上"从网上下载的 app 一律要求签名"这条硬拦，还要把二进制的下载、安装、更新链路补上：而 `pack-offline.py`、skills.sh、两个插件市场**没有一条**是为分发二进制设计的。**［设计推断］**
