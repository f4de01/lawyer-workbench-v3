## 0. 一句话结论

四格里**只有 Windows 侧两格有可无人值守的渲染通道**，而且两格用的是同一套调用形态：WPS Windows 的 Writer COM 把 Word 的对象模型连方法名带参数表照搬了一遍，gate.py 现在那三句（`Documents.Open` / `ComputeStatistics(2)` / `ExportAsFixedFormat(out, 17)`）在 WPS 上逐字成立。mac 侧两格都没有可无人值守的通道：mac + WPS 已实测坐实压根没有 API；mac + Word **API 齐全，卡在授权上**，而且卡它的两道关口（TCC Automation、Office 沙箱的按文件授权）都有厂商一手文档为据，其中沙箱那道是微软自己写的「cannot run unattended」。

**这三条都在加固图 #54 的中心假设，没有一条动摇它。**

## 2. mac + WPS（律师主力）

已实测坐实，结论不变，详见 `docs/research/mac-实测-20260907.md`（票 #41，2026-09-07 在律师那台 Mac 上跑出）：

- `/Applications/wpsoffice.app/Contents/MacOS/wpscli` 是纯 PDF 工具箱，只有 `pdf2*` 与 `photo2pdf` / `cad2pdf`，**没有 `docx2pdf` 一类子命令**；三种写法均 `Error(200): Invalid subcommand`。
- WPS for Mac 的 bundle 里 **没有 `.sdef`**，`Info.plist` 里没有 `NSAppleScriptEnabled` / `OSAScriptingDefinition`。它只响应 Standard Suite 最基本的 `activate` / `open` / `print`；`document` 不理解 `count` / `name` / `save` / `close`，`save as ... file format format PDF`、`export`、`compute statistics`、`repaginate` 一概 `-2740`（术语不存在）。

**这一格没有渲染通道，且已经是实测过的事实，不是文档推断。** 唯一没走死的缝是 `print front document` 退出码 0，但要无人值守就得建 CUPS 的 PDF 打印队列（需 sudo、输出路径不可控、WPS 的 `print` 不接受目标打印机参数），已由图 #54 明确划出 Out of scope。

**可信度：已实测坐实。**

## 3. Windows + Word（今天在跑的那条）

现行实现在 `skills/loo0ng-to-docx/scripts/gate.py` 的 `PS_RENDER` + `render_pdf`：`powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <base64 UTF-16LE>`，脚本体是

```powershell
$w = New-Object -ComObject Word.Application
$w.Visible = $false
$w.DisplayAlerts = 0
$d = $w.Documents.Open('<in>', $false, $true, $false)   # ConfirmConversions=false, ReadOnly=true, AddToRecentFiles=false
$null = $d.ComputeStatistics(2)                          # wdStatisticPages，逼它完成分页
$d.ExportAsFixedFormat('<out>', 17)                      # wdExportFormatPDF
$d.Close(0)
$w.Quit()
```

已知坑（均已在 ADR-0006 附注里落档，是本项目自己踩出来的实测事实）：

1. **导出前必须先 `ComputeStatistics(2)` 逼分页**，否则带页脚 PAGE 域的多页文书导出后 Word 崩掉（`RPC_E_DISCONNECTED`），3-1、4-2 两件模板稳定复现。
2. **Codex 的 workspace-write 沙箱里起不来 Word COM**：`0x80070520`「指定的登录会话不存在」。门禁那一步必须在沙箱外跑。
3. 超时预算：`render_pdf` 给了 **120 秒**，并在非 `NOWORD` 失败时整体重试一次（Word 偶发瞬时失败）。这远超 Codex shell 的默认 10 秒 / 上限 30 秒（ADR-0006），所以这一条**本来就不在 Codex 的 shell 预算内**，靠的是在沙箱外单独跑。
4. 开发机上无方正字体，Word 用替换字体量几何：这把尺子从第一天起就是**几何代理**，不是保真基准（图 #54 已核过的事实 2）。

开发机本机事实（2026-09-07 只读读取）：Word `16.0.20326.20132`，`C:\Program Files\Microsoft Office\Root\Office16\WINWORD.EXE`（x64）；`HKCR\Word.Application` → `CLSID {000209FF-0000-0000-C000-000000000046}` → `LocalServer32 = ...\WINWORD.EXE /Automation`，`CurVer = Word.Application.16`。

**可信度：在跑，已坐实。**

## 4. Windows + WPS

### 4.0 先更正一条票面前提：开发机上其实装着 WPS

票 #56 与图 #54 都写「Windows+WPS 开发机上也没装 WPS」。**这条不成立。** 开发机上 WPS Office **12.1.0.23542（x86）装在 `D:\wps\WPS Office\12.1.0.23542`**，`office6\wps.exe` 在，COM 注册项齐全（`HKLM\SOFTWARE\Kingsoft\Office\6.0\Common` 的 `InstallRoot` 指向它，`Architecture = x86`）。

因此本节大部分内容不是「查文档推断」，而是**在本机只读地读注册表与读 `wpsapi.dll` 的二进制串**得到的一手事实。**本节没有启动过 WPS，也没有创建过任何 COM 对象**，所以仍然不算行为实测；但它的可信度显著高于「查文档」。

### 4.1 ProgID：`KWPS.Application` 与 `WPS.Application` 都在，且都是 32 位注册

本机注册表实证：

| ProgID | CurVer | CLSID | LocalServer32 |
| --- | --- | --- | --- |
| `KWPS.Application` | `KWPS.Application.9` | `{000209FF-0000-4b30-A977-D214852036FF}` | `D:\wps\WPS Office\12.1.0.23542\office6\wps.exe /Automation` |
| `WPS.Application` | `WPS.Application.6` | `{000209FF-0000-4b30-A977-D214852036FE}` | 同上 |

两个 ProgID 的 `(Default)` 值都是 `WPS Writer Application Class`，指向同一个 `wps.exe`。表格组件另注册 `KET.Application` / `ET.Application`，演示组件 `KWPP.Application` / `WPP.Application`；另有一个大小写变体 `Kwps.Application`。

两条要点：

1. **CLSID 是刻意仿 Word 的**：Word 的 `Application` CLSID 是 `{000209FF-0000-0000-C000-000000000046}`，WPS 取 `{000209FF-0000-4b30-A977-D214852036FF}`，第一段 `000209FF` 一模一样；类型库 GUID 同理（Word 是 `{00020905-...}`，WPS 是 `{00020905-0000-4b30-A977-D214852036FF}`，注册名 `Upgrade Kingsoft WPS 3.0 Object Library (Beta)`，实现文件 `office6\wpsapi.dll`）。这是「按 Word 的样子做一套」的直接证据。
2. **注册只在 32 位视图里**：`HKCR\CLSID\{000209FF-0000-4b30-A977-D214852036FF}` 在 64 位视图下**不存在**，`/reg:32` 下才有（类型库同样只登记 `win32`）。而 ProgID 键（`HKLM\SOFTWARE\Classes\KWPS.Application`）不受 WOW64 重定向，两个视图里都看得见。

   直接后果：**64 位进程里 `New-Object -ComObject KWPS.Application` 会先把 ProgID 解成 CLSID、再在 64 位 CLSID 表里找不到它**。机制是 WOW64 的注册表重定向：`Software\Classes\CLSID` 走重定向、32 位进程看到的是 `Wow6432Node\CLSID`，而 ProgID 键是共享的（Microsoft Learn，[Registry Keys Affected by WOW64](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys)、[Registry Redirector](https://learn.microsoft.com/en-us/windows/win32/winprog64/registry-redirector)）。**本机实证 + 一手文档（机制）。** 所以真要驱动 WPS，得走 32 位的 PowerShell（`C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`）。**具体错误码（预期 `0x80040154 REGDB_E_CLASSNOTREG`）需实测。**

### 4.2 对象模型：`wpsapi.dll` 里逐字带着 Word 的方法名与参数表

本机实证，`office6\wpsapi.dll`（8.5 MB）中直接读出的接口串：

| gate.py 现在用的调用 | WPS 里的对应项 | 参数表 |
| --- | --- | --- |
| `Documents.Open(FileName, ConfirmConversions, ReadOnly, AddToRecentFiles)` | `KyWpsDocuments::Open` / `::Open2000` | `Open2000` 为 `FileName, ConfirmConversions, ReadOnly, AddToRecentFiles, PasswordDocument, PasswordTemplate, Revert, WritePasswordDocument, WritePasswordTemplate, Format, Encoding, Visible`；`Open` 更长，末尾是 `..., Repair, DocumentDirection, NoEncodingDialog, XMLTransform`。**与 Word 的位置参数逐位对齐**，gate.py 的 `Open(in, $false, $true, $false)` 原样成立 |
| `Document.ComputeStatistics(2)` | `KyWpsDocument::ComputeStatistics` | `WdStatistic Statistic, VARIANT* IncludeFootnotesAndEndnotes, long* prop`；枚举名 `wdStatisticPages` 也在库里 |
| `Document.ExportAsFixedFormat(out, 17)` | `KyWpsDocument::ExportAsFixedFormat` | `OutputFileName, WdExportFormat ExportFormat, OpenAfterExport, WdExportOptimizeFor OptimizeFor, WdExportRange Range, From, To, WdExportItem Item, IncludeDocProps, KeepIRM, WdExportCreateBookmarks CreateBookmarks, DocStructureTags, BitmapMissingFonts, UseISO19005_1, FixedFormatExtClassPtr`。**与 Word 的 `ExportAsFixedFormat` 签名逐参数一致** |
| `Application.Visible` / `.DisplayAlerts` / `.Quit()` | `KyWpsApplication::put_Visible`（`VARIANT_BOOL`）、`put_DisplayAlerts`（`WdAlertLevel`）、`Quit` | 一致 |

另有 `KyWpsDocument::SaveAs2`（参数表末尾 `..., AddBiDiMarks, CompatibilityMode`，与 Word 的 `SaveAs2` 一致）、`Repaginate`、`FitToPages`；枚举名 `wdFormatPDF`、`wdExportFormatPDF`、`wdExportFormatXPS`、`wdFormatXPS` 都在库里。

枚举的**数值**是否与 Word 相同，本机只读扫串取不出来（值存在类型库的二进制里）。**但金山有一手文档，答案是相同**，见 4.5。

### 4.3 关键问题：WPS 会不会占用 `Word.Application` ProgID

**本机实证：不会。至少在「WPS 已安装、但未设为默认办公套件」这个状态下不会。**

开发机上 WPS 装着，而：

- `HKCR\Word.Application`（64 位与 32 位两个视图都查过）→ `CLSID {000209FF-0000-0000-C000-000000000046}` → `LocalServer32 = C:\Program Files\Microsoft Office\Root\Office16\WINWORD.EXE /Automation`，`CurVer = Word.Application.16`。**没有被改写。**
- `HKCU\SOFTWARE\Classes` 下**没有** `Word.Application`（COM 劫持最常见的做法是往每用户 Classes 里插一份盖住 HKLM 的；这里没有）。
- `HKCR\.docx` 与 `HKCU\...\FileExts\.docx\UserChoice` 都是 `Word.Document.12`，即本机 WPS 也没抢文件关联。

**结论**：`gate.py` 在「Windows + 装了 WPS」上 `New-Object -ComObject Word.Application` **不会误拿到 WPS**。ProgID 是分开的两套，WPS 用自己的 `KWPS.Application` / `WPS.Application`。

**仍未证实的边角**：本机 WPS 没有被设为默认办公套件（`.docx` 关联在 Word 上）。**「把 WPS 设为默认办公套件之后，`Word.Application` 会不会被改写」这一问没有被本机状态回答，也没查到金山的一手说明。** 从常见做法看，「默认办公套件」改的是文件关联（`HKCR\.docx` → `kingsoftoffice.wps.docx` 一类）与 shell 动词，与 COM 的 `Word.Application` ProgID 是两件事；但**这一条记为需实测**，不靠推测填。

真要防守，一条**零成本的自证**就够：拿到对象后读 `Application.Path`（`KyWpsApplication::get_Path` 存在，Word 也有），Word 返回 `...\Office16`，WPS 返回 `...\office6`，两者一眼可分。

**不要用 `Application.Name` 分辨**：`wpsapi.dll` 里 `KyWpsApplication::get_Name` 之后紧跟着 UTF-16LE 的 `default` 与 `Microsoft Word` 两个串，强烈指向 **WPS 的 `Application.Name` 就返回 `"Microsoft Word"`**（Word 兼容垫片）。这是二进制串证据，**数值本身需实测确认**，但足以说明 `.Name` 不可作判据。另一个稳妥判据是查 WPS 独有成员，例如 `Application.OfdExportOptions`（OFD 是国标版式文档，Word 没有）。

### 4.4 无人值守的已知坑

- **必须走 32 位 PowerShell**（见 4.1）。附带一条好消息（本机实证）：Word 把自己的 CLSID **两个视图都注册了**（`HKCR\CLSID\{000209FF-0000-0000-C000-000000000046}\LocalServer32` 在 `/reg:32` 下也在，指向同一个 x64 的 `WINWORD.EXE`，跨位数走 `LocalServer32` 进程外 COM 本来就成立）。**所以 32 位的 `powershell.exe` 里 `Word.Application` 与 `KWPS.Application` 都能解析**，一条命令行就能先试 Word、再退而试 WPS，不必为两个引擎分别开两种宿主。
- **个人版的弹窗**：WPS 个人版（本机装的就是 `wps.exe` 这一套）有稻壳推广、登录提示等首启界面。`Application.Visible = $false` **金山官方文档明写支持**（见 4.5），但**它能不能把推广与登录那类窗口一起压住，官方与旁证都没说，需实测**。另有一条强制登录的注册表开关（旁证）：`HKCU\Software\kingsoft\Office\6.0\plugins\officespace\flogin` 下的 `enableForceLoginForHasInstallDevice`（新版）/ `enableForceLoginForFirstInstallDevice`（旧版）设为 `false`（<https://blog.csdn.net/zhr199970910/article/details/148283897>）。
- **进程残留**：旁证指出 WPS 有进程守护加 CEF 多进程架构，`wpscloudsvr.exe` / `wpscloudlaunch.exe` 一类在主程序关闭后仍驻留，杀子进程会被主进程拉起。**`Application.Quit()` 之后不能假定进程已退**，孤儿清理要单独兜底（比 Word 多一层）。需实测。
- **另一条通道（未展开）**：WPS 随包带 Kingsoft 虚拟打印机（`office6\kvprinter\`，`PrinterName = WPS Print to PDF`）。这是打印管线而非导出，输出路径不可控，与 mac 上那条 CUPS 缝同类，同样不建议走。

### 4.5 金山其实有一手的 COM 文档，而且它把枚举值钉死了

**先更正本节早先的一处判断**：金山不是「只有 JS 加载项文档、COM 面无文档」。金山在自家 CDN 上托管着一整套 WinCHM 编译的《WPS 开发人员参考》，结构与微软的 Word VBA 参考一一对应（对象 / 属性 / 方法 / 事件 / 枚举），并明确写了「使用自动化（以前称为 OLE 自动化）从另一个应用程序控制 WPS」。站点根：<https://qn.cache.wpscdn.cn/encs/doc/office_v13/index.htm>（同址另有 v11 / v12 / v14 / v15 / v19 目录，v13 是能稳定取到全文的那个）。新的 `open.wps.cn` 开放平台文档是 SPA、主打 JS 加载项，COM 那一章在新站上没找到。

**一手确认的官方 ProgID**（散在各组件的「Application 对象」页示例里，没有一览表）：文字 `Kwps.Application`、表格 `ket.application`、演示 `Kwpp.Application`。**`WPS.Application` / `ET.Application` / `WPP.Application` 在金山文档里一个字都没有**，但本机注册表里确实注册着（4.1），即「存在但无官方文档」。ProgID 大小写不敏感。

**枚举数值：与 Word 完全相同，一手文档确认。** 这条把 4.2 里那个未决项结掉了：

| 枚举 | 值 | 出处 |
| --- | --- | --- |
| `wdExportFormatPDF` | **17**（`wdExportFormatXPS` = 18） | 官方《WdExportFormat 枚举》页，另注「已添加版本：WPS 2015」 |
| `wdFormatPDF` | **17**（`wdFormatXPS` = 18） | 官方《WdSaveFormat 枚举》页 |
| `wdStatisticPages` | **2** | 官方《WdStatistic 枚举》页 |

**所以 gate.py 里那三个魔数（`ComputeStatistics(2)`、`ExportAsFixedFormat(out, 17)`）在 WPS 上按官方文档是等价的。**

方法签名也逐条有官方页面且与 Word 一致：`Documents.Open`（十六个参数，序列与 Word 相同）、`Document.SaveAs2`、`Document.ExportAsFixedFormat`（十五个参数逐字一致）、`Document.ComputeStatistics(Statistic, IncludeFootnotesAndEndnotes)`、`Application.Visible`（官方示例原文「本示例隐藏 WPS：`Application.Visible = false`」）、`Application.DisplayAlerts`（类型 `WdAlertLevel`）、`Application.Quit`。这与 4.2 从 `wpsapi.dll` 里扫出来的东西互相印证。

**关于个人版**：金山官方明说**个人版不带 VBA 宏环境**，宏只在专业版增强版与 WPS+ 里有（<https://www.wps.cn/learning/room/d/212673>、<https://www.wps.cn/learning/room/d/302526>）。但那说的是**在 WPS 内部跑宏**；**外部进程经 COM 驱动 WPS 能不能在个人版上用，金山一句话没有**，旁证还互相打架（同一位作者 2024 年说能、2025 年说个人版把顶层 `Application` 接口封死了）。**本机 12.1.0.23542 已注册 ProgID 这一事实比那两条互斥旁证更可信，但结论仍是需实测。**

### 4.6 这一格最大的风险不是错报，是 WPS 自己会把 COM 面搞没

WPS 官方社区有一帖（<https://bbs.wps.cn/topic/62639>，2025-08，浏览近万）标题就是「近期发布的 WPS Office 最新版本（**12.1.0.22529 与 12.1.0.22525**），COM 自动化接口失效」，正文称「**所有 WPS ProgID（包括 `KET.Application`、`KWPS.Application`、`KWPP.Application` 等）连接失败**」「使用自带的配置修复工具-注册组件，也无法修复」，而降到 2025 夏季版或 WPS 2019 就正常。**帖内到 2026-06 仍无任何金山官方回复。** 旁证，但来源是金山自家社区。

**含义：WPS 的 COM 面没有兼容性承诺，会随小版本整段消失。** 对「出件」这种必须可重复的链路，这是结构性风险，**比「会不会错拿到 WPS」严重得多**。所以第二层渲染器把 WPS 当后备时，必须能在拿不到引擎时干净地退回第一层，而不是把整条出件流程挂在它上面。

### 4.7 关于劫持，补一条反方向的孤证

我在 4.3 用本机注册表证明了 `Word.Application` 没被占用。文档侧的补充：

- **金山从未有任何 KB 说过它会接管 `Word.Application`**，也没有「如何恢复 `Word.Application` 指向 Word」的官方文章。查不到。
- 已被旁证坐实会被 WPS 改写的是 **`Word.Document.12` / `Excel.Sheet.12` / `PowerPoint.Show.12` 这类文档 ProgID 的 `\Shell\Open\command`**，也就是**文件关联**，与 automation ProgID 是两回事。官方侧对应的是配置工具里的「设置文件关联」（<https://www.wps.cn/learning/room/d/226767>）。
- **唯一一条指向 COM ProgID 劫持的孤证**：一篇 2023 年的 CSDN 文章（<https://blog.csdn.net/XIWCX/article/details/134976730>）里，作者用 `Word.Application` 加 `ExportAsFixedFormat` 转 PDF 报「无效的类字符串」，其结论是「计算机内 wps 未注册 word/excel 等 COM 组件」，修法是「wps 配置工具 → 高级 → 重置修复 → **重新注册组件**」，修完即可用。**若如实描述，就意味着 WPS 的「重新注册组件」会把 `Word.Application` 注册到自己身上。** 单一来源、没贴注册表、也没排除他机器上装过又卸掉 Office，**记为需实测**。
- 反向证据同样存在：纯 WPS 机器上 `Excel.Application` 报「没有注册类」（<https://blog.csdn.net/yueyi0221/article/details/137796008>），且社区通行做法是**先判断装的是 Office 还是 WPS 再分别用两套 ProgID**，如果会被劫持这套做法就没必要存在。
- **金山配置工具里那个「兼容第三方系统和软件」勾选到底往注册表写什么，金山从未公开，查不到。** 官方只说它在哪（<https://www.wps.cn/learning/room/d/329859>）。

**处置：不要假设 `Word.Application` 一定是 Word，也不要假设它一定不是。** 风险面是「静默拿到 WPS」而不是「报错」，所以脚本必须在拿到对象后自证引擎。最硬的判别不是任何一个属性，而是读 `HKCR\Word.Application\CLSID` → `HKCR\CLSID\{...}\LocalServer32` 看它指向哪个 exe（本文 4.3 用的就是这条），其次是 `Application.Path`（金山文档里该页的示例值恰好是 `C:\WPSOffice`，是四个属性里唯一有官方字面线索的）。

## 5. mac + Word

一句话：**API 是齐的，卡的是授权。** 转 PDF 这条 AppleScript 路在字典里明确存在，写法也确定；但 macOS 与 Office 自身的三道授权关口里，**至少两道在非 MDM 环境下没有合法的免人工解**，其中一道还是微软自己白纸黑字写的「cannot run unattended」。

### 5.1 字典是完整的对象模型，`format PDF` 确切存在

Word for Mac 出厂的 `Microsoft Word.sdef`（可用 `sdef /Applications/Microsoft\ Word.app` 自取；本轮比对的是 Office 2016 版本的公开转储 <https://github.com/doekman/sdef/blob/master/Office%202016/Microsoft%20Word.sdef>）里确认有：

- `application` 类，含 `document` / `window` 元素；`open`（直接参数 `file`，返回 `document`）、`close`、`print` 走 Standard Suite。
- `save as`：`<command name="save as" code="sWRD1420" description="Saves the document with a new name or format.">`，可选参数 `file name`（text）与 `file format`（`WdSaveFormat`）。
- `compute statistics`（`sWRDWpSS`）与 `repaginate`（`sWRD1421`）都在。
- 枚举：`<enumerator name="format PDF" code="0x02310010"/>`。**确切术语就是两个词的 `format PDF`**，没有 `format PDF export` 这种写法。

**可信度：一手（出厂 sdef 制品）。** 注意这是「随应用出厂的字典」，不是微软发布的文档，两者不是一回事，见 5.2。

**一个必须记下的坑：Mac 端 AppleScript 的枚举数值与 Windows VBA 的不一样。** sdef 里 `format PDF` 是 `0x02310010`（低位 16），而 VBA 的 `wdFormatPDF` = 17（[WdSaveFormat enumeration (Word)](https://learn.microsoft.com/en-us/office/vba/api/word.wdsaveformat)）。**Mac 侧永远写名字 `format PDF`，绝不能照抄 Windows 的裸整数 17。** 一手文档确认。

（顺带把 Windows 侧那个 17 也钉死：`wdExportFormatPDF` = 17，见 [WdExportFormat enumeration (Word)](https://learn.microsoft.com/en-us/office/vba/api/word.wdexportformat)，即 gate.py `ExportAsFixedFormat('{OUT}', 17)` 里的 17。一手文档确认。）

### 5.2 微软自 Office 2004 之后没再发过 AppleScript 参考手册

Microsoft Q&A 上《Word 2011 AppleScript Reference》被采纳的回答原话：「As far as I know, Microsoft has not produced any substantial Applescript documentation since the 2004 version of Office.」（<https://learn.microsoft.com/en-us/answers/questions/4825342/word-2011-applescript-reference>）该帖给出的 `Word2004AppleScriptRef.pdf` 官方下载链接**现已 404**。

搜遍 learn.microsoft.com，**微软没有任何关于 Word for Mac AppleScript 支持被弃用或仍被维护的正式表态**。查不到。

**由此带出本节最大的未知项**：现行 365 版本的字典是否仍完整。旁证两条，方向相反：Word **16.44**（Catalina，2020-12）上 `save as ... file format format PDF` 被报「works perfectly」（<https://forum.keyboardmaestro.com/t/applescript-save-microsoft-word-doc-x-document-to-pdf/20614>）；Word **16.70**（2023-02）上同一脚本报 `-1708 active document doesn't understand the "save as" message`，同帖有人断言「AppleScript support is broken in Word v16.70 ... Only Microsoft can fix this」（同链接；另见 <https://forum.latenightsw.com/t/microsoft-word-doesnt-understand-the-save-as-message/4187>）。16.71 及之后是否修复**查不到**（Office for Mac 官方 release notes 里检索 `AppleScript` 零命中）。**需实测。**

### 5.3 确切写法

```bash
/usr/bin/osascript <<'AS'
with timeout of 180 seconds
  tell application id "com.microsoft.Word"
    set display alerts to alerts none                  -- sdef: WdAlertLevel
    set d to open POSIX file "/tmp/in.docx"
    repaginate d
    compute statistics d statistic statistic pages     -- 对应 Windows 的 ComputeStatistics(2)
    save as d file name "/tmp/out.pdf" file format format PDF
    close d saving no
    quit
  end tell
end timeout
AS
```

`save as` / `format PDF` / `repaginate` / `compute statistics` / `display alerts` 五处均以 sdef 为据（一手）。生产中在用的等价 JXA 写法是 `doc.saveAs({fileName: out, fileFormat: "format PDF"})`（旁证：`docx2pdf` 的 <https://github.com/AlJohri/docx2pdf/blob/master/docx2pdf/convert.jxa>）。

### 5.4 Windows 那个 `ComputeStatistics(2)` 坑在 Mac 上有没有等价物

**先更正一处认识**：Windows 侧那条坑（不先逼分页就导出会崩）**在微软官方文档里根本没写**，它是本项目自己踩出来的经验事实（ADR-0006 附注）。所以 Mac 侧自然也查不到对应说法。

Mac 侧的 API 都在（sdef 一手）：`repaginate`、`compute statistics ... statistic pages`、`Word options` 上的 `pagination`（背景重排开关）、`update field` / `update page numbers`、`update fields at print`。**但 `application` 类上没有 `ScreenUpdating` 属性**，只有 `screen refresh` 命令。

同类现象在 Mac 上有旁证：Microsoft Q&A 上有用户在 Office 16.64 报 PAGE/NUMPAGES 显示成「1 of 2, 1 of 8, 3 of 8」，MVP 回复「The on-screen display is an approximation ... it will likely force re-pagination」（<https://learn.microsoft.com/en-us/answers/questions/5176644/page-numbering-is-not-shown-correctly-until-after>）。

**导 PDF 时是否自动更新 PAGE 域：文档没说，需实测。** `update fields at print` 只覆盖打印路径，不覆盖 `save as ... format PDF`。防御写法（`repaginate` + `compute statistics` 各一句）成本极低、与 Windows 侧对齐，建议照做；是否必要需实测。

### 5.5 无人值守的三道关口

**关口一：macOS 的 TCC Automation 同意框。非 MDM 环境下无法预授权。一手文档确认。**

苹果自家的 MDM schema 仓库里，PPPC payload（`com.apple.TCC.configuration-profile-policy`）的元数据写着 `allowmanualinstall: false` 与 `userapprovedmdm: true`（<https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.TCC.configuration-profile-policy.yaml>）。**`allowmanualinstall: false` 就是答案**：双击 `.mobileconfig` 装不上，必须由已被用户批准的 MDM 经设备通道下发。有 MDM 时，`Services.AppleEvents` 里配 `Identifier`（发起方，如 `/usr/bin/osascript`）+ `AEReceiverIdentifier`（`com.microsoft.Word`）+ 两边的 `CodeRequirement`，`Allowed: true` 之后官方描述是「the user isn't prompted and can't change this value」（另见 <https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web>）。

其余路子逐条否掉：

| 手段 | 结论 | 出处 |
| --- | --- | --- |
| `tccutil` | **只有 `reset`**，没有 grant / allow | 旁证 <https://ss64.com/mac/tccutil.html>（与 Apple man 页一致） |
| 直接改 `TCC.db` | 要先关 SIP | 旁证 <https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-tcc/index.html> |
| `com.apple.security.automation.apple-events` entitlement | **不免除授权**。苹果原文只说它表示 app「may prompt the user for permission」 | 一手 <https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.automation.apple-events> |
| `NSAppleEventsUsageDescription` | 只是弹窗**文案**，10.14+ 必填 | 一手 <https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription> |

律师那台是个人 Mac，没有 MDM。**所以这一关在本项目的现实里是死的。** 注意它是**一次性**的：人点一次之后就长期有效，所以严格说是「首次需人值守」，不是「每次都要人」。

**关口二：Office 的沙箱文件访问。微软自己写了「cannot run unattended」。一手文档确认。**

微软《Request access to multiple files》原文：「Because the Office 2016 for Mac apps are **sandboxed**, they don't have permission to access external files. ... **This means that macros that access external files cannot run unattended. The user must approve file access the first time each file is referenced.**」（<https://learn.microsoft.com/en-us/office/vba/office-mac/grantaccesstomultiplefiles>）

**要紧的边界**：这段话讲的是 **VBA 宏访问外部文件**。经 AppleScript 的 `open POSIX file "/path"` 打开时，Word 是否走同一条 powerbox 授权链、是否同样弹窗，**微软文档没说，需实测**。可能的绕法是把输入输出都放进 Word 自己的容器 `~/Library/Containers/com.microsoft.Word/Data/`，**同样需实测**。

这一关比关口一狠：它是**按文件**授权的，不是一次点完就完事，而本项目每出一版都是一个新文件。

**关口三：Word 自身的首启弹窗。这一关能压掉，一手文档确认。**

微软官方的 Office for Mac 首选项文档（<https://learn.microsoft.com/en-us/microsoft-365-apps/mac/preferences-office>、<https://learn.microsoft.com/en-us/microsoft-365-apps/privacy/mac-privacy-preferences>）给了文档化的键：`OfficeAutoSignIn`（原文「This key suppresses first run dialogs」）、`ShowWhatsNewOnLaunch`、`ShowDocStageOnLaunch`、`DiagnosticDataTypePreference`；批量授权装机用 VL Serializer 可免激活提示。**但同页写明「If users have already gone through the first run experience, the profiles don't affect them.」** 律师那台早就用过 Office 的话，这些键补不回去。

（社区常传的 `kSubUIAppCompletedFirstRunSetup1507`、`SendAllTelemetryEnabled` **在微软文档里查不到**，只有博客来源，是旁证。）

**另外：没有 headless / invisible 模式，且必须有 Aqua 登录会话。一手文档确认。**

sdef 的 `application` 类上**没有 `visible` 属性**（`visible` 只出现在 `window` 与命令栏上），所以不能像 Windows 那样 `$w.Visible = $false`；要藏窗口只能再经 System Events 改进程属性（`docx2pdf` 就是这么干的），而那是**另一个 AppleEvents 接收方，要再授权一次**（推断，需实测）。苹果 Technical Note TN2083 原文：daemon「is not allowed to connect to the window server」（<https://developer.apple.com/library/archive/technotes/tn2083/_index.html>）。**这条通道跑不了纯后台，必须有人登录着图形会话。**

### 5.6 超时

`osascript` 默认等应用响应 **120 秒**，且超时后「AppleScript does not cancel the operation, it merely stops execution of the script」（一手：[AppleScript Language Guide, control statements](https://developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_control_statements.html)）。**运维含义**：10 秒就砍掉，会留下一个半开的 Word 和一个可能写了一半的 PDF。

Word for Mac 的冷启动耗时**微软没有任何官方数据，查不到**。旁证一致指向「`open` 返回时文档还没就绪」：社区脚本普遍在 `open` 后加 `delay 1` 或轮询 `repeat while not (active document is not missing value)`。**判断：Codex 的 10 秒默认几乎肯定不够，30 秒上限也偏紧**（这一判断是推断，需实测）。更糟的是，一旦触发 TCC 或沙箱弹窗，脚本会**挂到 120 秒默认超时**才报错，在 30 秒的 harness 下表现为「被杀」而不是一个可读的错误。

## 6. `soffice --headless --convert-to pdf`（机会性第三后端）

LibreOffice 在图 #54 里**不作前提**（Out of scope 明写不当必装项），只作「机器上碰巧有就用」的机会性后端。**本机与律师那台 Mac 上都没有装**（Mac 见 `docs/research/mac-实测-20260907.md` 的机器表；开发机上 `soffice` 不在 PATH，三个常见安装路径都不存在，本机实证）。所以这一节纯查文档。

**先说这一节最要紧的一条**：把 LO 的 PDF 页数当 Word 的页数用，**在 LibreOffice 26.2 之前是系统性偏小的**，原因是 CJK 行高的 Word 兼容修正 26.2 才落地（见 6.5）。而本项目用渲染器就是为了量页面几何。**这一条把 LibreOffice 从「可以顺手用的加信后端」降成「必须先读版本号、并在报告里标出已知偏差的后端」。**

### 6.1 命令行形态（一手文档）

出处：LibreOffice 官方帮助 [Starting LibreOffice Software With Parameters](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)、官方 man page [`libreoffice.1`](https://raw.githubusercontent.com/LibreOffice/core/master/sysui/desktop/man/libreoffice.1)。

- 语法：`--convert-to OutputFileExtension[:OutputFilterName[:OutputFilterParams[,param]]] [--outdir output_dir]`。官方示例逐字包含 `--convert-to pdf *.doc` 与 `--convert-to pdf:writer_pdf_Export --outdir /home/user *.doc`，**所以过滤器名 `:writer_pdf_Export` 不是必需的**。
- **`--convert-to` 自带 `--headless`**：man page 原文「It implies `--headless`」。
- **`--headless` 自带 `--invisible`**：man page 原文「strictly ignores any GUI environment」（内置 `--help` 文本里没有这句）。
- 「In absence of `--outdir`, current working directory is used for the result.」
- **输出文件名不可指定**，只能落在 `--outdir` 下、沿用输入 basename。这是已知的未实现需求（[tdf#152192](https://bugs.documentfoundation.org/show_bug.cgi?id=152192)、[tdf#78523](https://bugs.documentfoundation.org/show_bug.cgi?id=78523)，均 NEW）。已存在的输出会被覆盖。
- **Windows 上要用 `soffice.com`**，见 6.7。
- 标志现状：`--norestore`、`--nologo`、`--nodefault` 现行；**`--nolockcheck` 对 headless 冗余**（源码里该检查本就在 `IsHeadless() || IsInvisible()` 时跳过）；**`--nofirststartwizard` 已是空操作**，官方帮助把它列在「Ignored switches」下，原文「Does nothing, accepted only for backward compatibility.」，**别再抄这个参数**；**`--safe-mode` 绝不能用于无人值守**，官方明写进入后会弹一个三选一的 profile 恢复对话框（<https://help.libreoffice.org/latest/en-US/text/shared/01/profile_safe_mode.html>）。
- JSON 形式的 FilterOptions（`pdf:writer_pdf_Export:{"PageRange":{"type":"string","value":"2-5"}}`）有专门的官方页面并给出 CMD / PowerShell / bash 三种转义写法（<https://help.libreoffice.org/latest/en-US/text/shared/guide/pdf_params.html>），**引入版本是 LibreOffice 7.4**（[7.4 Release Notes](https://wiki.documentfoundation.org/ReleaseNotes/7.4)）。

### 6.2 退出码：26.2 之前恒为 0（一手文档确认）

**这是这条后端最要命的一点。** [tdf#148275](https://bugs.documentfoundation.org/show_bug.cgi?id=148275)「Set error status to non 0 if headless conversion failed or aborted」2022 年开，RESOLVED FIXED，[修复提交](https://git.libreoffice.org/core/commit/633ce6b17007ea401aa5c013ec14308b14596d31)的机器人留言逐字写着「It will be available in **26.2.0**」。26.2.0 的公告周是 2026-01-26，距今只有几个月，**机会性遇到的机器上绝大多数 LO 都在 25.x 或更早，也就是转失败也给你 0**。

而且 26.2 的补丁只覆盖三种失败（无导出过滤器、`storeToURL` 抛异常、源文件加载不了）；同票里 Mike Kaganski 还指出状态需要经 IPC 回传给外层进程，补丁作者明说没做，**已有实例在跑时 26.2 的退出码也未必反映失败**。

26.2 之前拿到的非零码说明的是启动或崩溃，不是转换失败（`include/desktop/exithelper.h`：`77` 启动时 UNO 异常、`79` 崩溃后强制重启、`81` office 自我重启；[tdf#107912](https://bugs.documentfoundation.org/show_bug.cgi?id=107912) 那个「headless firstrun crashes (exit code 81)」就是 `EXITHELPER_NORMAL_RESTART`，结论是 NOTABUG）。

**替代检测手段**（源码 `dispatchwatcher.cxx` 逐字确认）：成功走 stdout，形如 `convert <src> -> <dst> using filter : writer_pdf_Export`；失败走 stderr，前缀 `Error:`（`source file could not be loaded` / `no export filter for <src> found, aborting.` / `Please verify input parameters...` / `Cannot create temporary file...`）。**Windows 上要拿到这两个流必须用 `soffice.com`。**

**判据只能落在「目标 PDF 存在且能被 PyMuPDF 打开」。** gate.py 现在对 Word 那条已经是这么写的（`r.returncode == 0 and pdf.is_file()`），照搬即可，但对 LO 还要把 `returncode == 0` 那半去掉。

### 6.3 单实例：官方明说第二个进程只是把参数转交给第一个

TDF wiki `UserProfile` 逐字（一手）：

> A single user profile must only ever be accessed by a single LibreOffice process. Internally, if a single user starts multiple LibreOffice processes that would all access the same user profile, **only the first process does any actual work**, like opening documents for editing, and **the excess processes pass on their command line arguments to the first one for processing**.

（<https://wiki.documentfoundation.org/UserProfile>）

**直接含义**：律师开着 LO 窗口时，门禁起的那个 `--headless --convert-to` 进程**不会自己干活**，它把命令行丢给 GUI 进程然后退出，而按 6.2 那个 IPC 缺口，退出码也不反映结果。旁证与之一致：TDF 社区论坛上有人在 macOS 实测「produces a brief 2nd LibreOffice in the Dock, but no PDF is created ... it only seems to work if LibreOffice is NOT running」（<https://communitytest.documentfoundation.org/t/speed-up-rtf-to-pdf-headless-conversions/57436>）；Windows 侧有 [tdf#129713](https://bugs.documentfoundation.org/show_bug.cgi?id=129713)（`--cat` 在有别的实例时不输出，与 `--convert-to` 同走一条 IPC 路径，NEW）。

**「在 Windows / macOS 上各自到底是静默 attach 还是明确报错」官方没有逐条描述，需实测。**

### 6.4 官方规避手段：每次一个独立 profile

`-env:UserInstallation` 是**官方的**，帮助页与 wiki 都给了逐平台示例，Windows 那条用的正是 `soffice.com`：

```
soffice.com -env:UserInstallation=file:///c:/my-test-profile
soffice     -env:UserInstallation=file:///tmp/test
open LibreOffice.app -env:UserInstallation=file:///tmp/test
```

wiki 另附一条必须遵守的约束：「The path to the user profile needs to be a proper URL; **some special characters, like spaces, need to be UTF-8-percent-encoded**」，例子是 `file:///c:/Folder%20Name%20With%20Spaces/my-test-profile`。**本项目的临时目录路径里若有空格或中文，必须先做百分号编码。**

TDF 自家的启动耗时基准脚本就是每次建一个全新临时 profile 再传 `-env:UserInstallation`（<https://opengrok.libreoffice.org/raw/dev-tools/perf/test-startup-time.py>）。

**代价**：独立 profile 只隔离 profile 与 IPC 管道，**不隔离冷启动成本**，等于每次都在付首启（见 6.6）。

### 6.5 保真：CJK 行高的 Word 兼容修正 26.2 才落地

官方自己把「和 Word 一致」定位成**一组可调开关**而非保证：`工具-选项-Writer-兼容性`页开篇即「These options help in fine-tuning LibreOffice when importing Microsoft Word documents.」，随后列出二十多条与分页直接相关的独立开关，**并注明出厂默认只开其中 6 条**（<https://help.libreoffice.org/latest/en-US/text/shared/optionen/01041000.html>）。

同一页有一条对本项目致命的开关，官方原文：

> Whenever Microsoft Word uses a CJK font to lay out text, **it applies an extra multiplier to the line height**. ... If the font reports coverage for any of the following code pages, the line height multiplier is applied: CP932 / **CP936 (Simplified Chinese)** / CP949 / CP950. Writer would respect the original font metrics when laying out DOC/DOCX files. **This change makes Writer try to emulate Microsoft Word behavior instead, subject to a compatibility flag.**

对应 bug 是 [tdf#129808](https://bugs.documentfoundation.org/show_bug.cgi?id=129808)，标题就是「FILEOPEN DOC/X: **Line spacing narrower than Word**」，2020 年开；两次关键提交的机器人留言分别是「It will be available in **25.2.0**」与「It will be available in **26.2.0**」（[后者](https://git.libreoffice.org/core/commit/e78940b7de0e3913a0b77c1874e162d8a63c6eb7) 即 `sw: Extend leading for CJK fonts in DOC/DOCX files`）。DOCX 导入器 `DomainMapper` 会把 `MsWordCompGridMetrics` 置 `true`，但 schema 默认是 `false`。

**推论（一手文档 + 一手 commit）：26.2 之前的 LibreOffice 打开中文 DOCX，行距比 Word 窄，每页多塞行，总页数与分页位置与 Word 不同，方向是系统性偏小。** 而且该 bug 至今仍在被标重复（2026-02 还并入 tdf#166952），说明未完全解决。

字体替换：官方定性是「缺字体时用操作系统的默认替换字体」「The replacement does not change the font settings that are saved in the document」（<https://help.libreoffice.org/latest/en-US/text/shared/optionen/01010700.html>），即**静默替换、无警告、无退出码信号**。结合本机无方正字体这条事实，中文文书里的字体在两台机器上都会走替换路径，**具体替换结果官方不输出，必须实测**。

字段更新：**PAGE 域会更新**。官方 `工具-选项-Writer-常规` 页有一张「无论 Fields 复选框如何都会更新」的表，其中逐字列出条件「Changing the page count」对应字段「Page」、条件「Printing the document (also exporting as PDF)」对应另一组字段（<https://help.libreoffice.org/latest/en-US/text/shared/optionen/01040900.html>）。**目录（TOC）没有任何官方说法表明 `--convert-to` 会刷新**，官方把索引更新写成用户手动动作；源码里 `UpdateDocMode` 只在普通打开文档那个分支设置，`REQUEST_CONVERSION` 分支只设 `ReadOnly / OpenNewView / Hidden / Silent`。**命令行没有控制字段或目录更新的开关**（`--infilter` 只接受过滤器名与该过滤器自己的参数），要控制得改走 UNO API。

同一段源码还显示：转换路径**不注册 `InteractionHandler`**，所以带密码的文档不会弹框，直接失败。

### 6.6 首启成本：10 秒肯定不够，30 秒也未必够

**TDF 自家的启动耗时基准脚本把单次「全新 profile + headless 打开一个文档」的超时设成 300 秒**（`importTimeout = 300`，<https://opengrok.libreoffice.org/raw/dev-tools/perf/test-startup-time.py>）；LO 自带的 Python bootstrap helper 默认重试延迟是 `(1, 3, 5, 7)` 秒，即官方预期「起进程到能接 UNO」是数秒量级。

旁证：TDF 社区论坛上的生产用例报「The initial conversion is about **5-10 seconds**. If we process a second document, it is **less than a second**. If we then wait a couple minutes and process a third document, **it goes back to the 5-10 seconds**.」（同 6.3 那个链接）；[tdf#170608](https://bugs.documentfoundation.org/show_bug.cgi?id=170608)（UNCONFIRMED）报一份 21 页、每页一张满页表格的文档在 26.2.0 上要约 30 秒。

**5 到 10 秒是「已装好、profile 已建、缓存热」的下限**，而本项目按 6.4 每次都要新建 profile，等于每次都付首启；再叠上中文字体缓存与表格密集文书的排版耗时。

还有确凿的**挂死**风险，全是 DOCX 转 PDF：[tdf#171646](https://bugs.documentfoundation.org/show_bug.cgi?id=171646)（NEW，headless 转某些 DOCX 挂住）、[tdf#168625](https://bugs.documentfoundation.org/show_bug.cgi?id=168625)、[tdf#163267](https://bugs.documentfoundation.org/show_bug.cgi?id=163267)（转到内存耗尽）、[tdf#170244](https://bugs.documentfoundation.org/show_bug.cgi?id=170244)（100% CPU 直到崩）。

**结论：这条后端不能挂在 10 秒 / 30 秒的同步 shell 调用上。** 要用就得独立起进程、轮询产物、超时后 kill `soffice.bin`（不是只 kill wrapper）。

### 6.7 Windows：一律用 `soffice.com`

官方原文：「Use `soffice.exe` instead of `soffice.com`, when you do not need console (e.g., you do not use command-line interface for headless operations).」

源码层面的真实差别（`Executable_soffice_com.mk` / `Executable_soffice_exe.mk` / `win32/source/loader.cxx`）：`.com` 是 console 子系统、继承控制台，`soffice.bin` 的 stdout/stderr 看得见；`.exe` 是 GUI 子系统、以 `DETACHED_PROCESS` 起 `soffice.bin`，**两个流全丢**。**两者的 loader 本身都会等**（同一份 `MsgWaitForMultipleObjects(..., INFINITE)`）并回传 `GetExitCodeProcess()`。

**所以「`soffice.exe` 会立刻返回」这个流传的说法要更正**：loader 并不提前返回，是 `cmd.exe` 在交互式命令行下不等 GUI 子系统程序；从 `subprocess.run` 这类直接 `CreateProcess` 加等句柄的调用方，`.exe` 也是会被等到的。**但仍然一律用 `.com`**，因为 26.2 之前 stderr 是唯一的失败信号来源。

Windows 的孤儿进程：loader 用 Job Object 管 `soffice.bin`，但转换挂死时仍需外部超时 kill `soffice.bin` 本身。需实测。

### 6.8 macOS 侧

- **不触发第 5 节那道 TCC Automation 授权框**：`soffice` 是普通可执行文件，不是经 Apple Events 驱动另一个 app。**这是它相对于 mac + Word 的唯一实质优势。**
- **但仍会撞上文件访问那类 TCC**：[tdf#152567](https://bugs.documentfoundation.org/show_bug.cgi?id=152567)（NEW）报「beachball for ~7 seconds until the permissions dialog showed up」。**`--headless` 下读写 `~/Documents`、`~/Desktop`、iCloud Drive 时是弹框、静默拒绝还是挂起，查不到，需实测**，这是 macOS 侧最大的未知数。规避办法是让输入输出都走非受保护路径。
- Gatekeeper：苹果原文「Gatekeeper also **requests user approval before opening downloaded software for the first time**」（<https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web>）。机会性场景下律师通常已手动开过 LO，风险不高；**直接 exec `Contents/MacOS/soffice` 绕过 LaunchServices 是否照样触发，查不到，需实测。**
- **`--invisible` 在 macOS 上仍露 Dock 图标**（[tdf#113601](https://bugs.documentfoundation.org/show_bug.cgi?id=113601)，ASSIGNED，2017 至今），`--headless` 实测观感相同（旁证）。无人值守时律师会看见图标闪一下。
- **macOS 没有 quickstarter**（旁证：TDF 论坛 QA 成员答「There is no LO quickstarter for Mac」），所以每次都是冷启动，无法靠常驻摊薄。

### 6.9 若真要用，最小可行形状

```bash
# macOS
/Applications/LibreOffice.app/Contents/MacOS/soffice \
  -env:UserInstallation=file:///<每次新建的临时目录，空格要 %20> \
  --headless --norestore --nologo --nodefault \
  --convert-to pdf:writer_pdf_Export --outdir <outdir> <in.docx>

# Windows（必须 .com）
"C:\Program Files\LibreOffice\program\soffice.com" ^
  -env:UserInstallation=file:///C:/<临时目录> ^
  --headless --norestore --nologo --nodefault ^
  --convert-to pdf:writer_pdf_Export --outdir <outdir> <in.docx>
```

调用方必须配的四条：

1. **不看退出码判成败**（除非确认 ≥ 26.2 且无并发实例），看产物是否生成，外加解析 stderr 的 `Error:` 前缀行。
2. **后台起 + 轮询 + 超时 kill `soffice.bin`**，超时按 60 秒以上设。
3. **每次新建 `-env:UserInstallation` 临时目录**，路径做百分号编码，用完删。
4. **先读一次 `soffice --version`**，低于 26.2 就在审查报告里把「页数可能偏小」作为已知偏差标出（CJK 行高，tdf#129808）。

## 7. 对第二层渲染器的建议

### 7.1 先建哪个

**第一优先，而且便宜得离谱：把现有那条 Word COM 通道从「只认 `Word.Application`」改成「先 Word、拿不到再 `KWPS.Application`」，宿主换成 32 位 `powershell.exe`。**

理由是本文第 4 节那一堆本机实证：脚本体一个字都不用改（`Documents.Open` 的位置参数、`ComputeStatistics` 的签名、`ExportAsFixedFormat` 的十五个参数在 WPS 里逐字一致），要动的只有两处，一处是 ProgID 的回退列表，一处是宿主的位数。**这一改把「Windows + WPS」这一格从未知变成有通道，投入是几行。**

枚举值也不用猜：金山一手文档确认 `wdExportFormatPDF` = `wdFormatPDF` = 17、`wdStatisticPages` = 2，与 Word 相同（4.5）。

配套要加的只有一句自证：拿到对象后读 `Application.Path`，把它写进审查报告的披露项，让人一眼看得出这一版是谁量的（Word 是 `...\Office16`，WPS 是 `...\office6`）。**不要用 `Application.Name` 分辨**，理由见 4.3。

**但要把它当「后备」而不是「第二条主路」**：4.6 那条说明 WPS 的 COM 面没有兼容性承诺，曾经在两个小版本里整段失效且金山没回应。所以接法必须是「拿不到就干净地退回第一层」，不能让出件流程挂在它上面。

**第二优先：把渲染这一步的失败形态做细。** 现在 `render_pdf` 的失败只有一个 `CannotRun`，而按本文查出来的东西，失败至少要分三类才对得上现实：拿不到引擎（`NOWORD` 类）、拿到了但导不出（`EXPORTFAIL` 类）、**卡在授权或弹窗上（新增）**。第三类是 mac + Word 那格的常态，表现是「挂到超时被杀」而不是一个可读的错误，在第一层降为门禁本体之后，它应当只影响加信、不影响结论。

### 7.2 哪个不值得建

**mac + Word 不值得为它建专门的通道。** 这不是因为 API 不行（API 是齐的、写法是确定的），而是因为：

1. **律师那台 Mac 上没有 Word**（`docs/research/mac-实测-20260907.md` 的机器表，Word、LibreOffice 都是「没有」）。要走这条路先得让律师装一套 Office。
2. 就算装了，**Office 沙箱是按文件授权的**，而本项目每出一版都是一个新文件，微软自己写了「cannot run unattended」。TCC 那道关口好歹是一次性的，沙箱这道不是。
3. **没有 headless 模式，必须有人登录着图形会话**，出件时 Word 会在律师眼前弹出来。
4. 现行 365 版本的 `save as` 到底还灵不灵，有 16.70 崩坏的旁证而没有一手结论，**在能上 Mac 之前这是个不能消除的风险**。

**结论：为 mac + Word 建通道的投入产出比，明显低于把同样的精力放在第一层的计算判据上。** 若将来律师那台装了 Word，值得做的也只是「机会性地试一次、失败就静默退回第一层」，而不是把它当成一条要维护的通道。

**mac + WPS 不必再查了。** 已实测坐实没有 API，剩下的缝（CUPS 虚拟打印队列）图 #54 已划出 Out of scope，本文没有查出任何推翻它的东西。

**LibreOffice 要降一档看待。** 本文查之前它像是「碰上装了就顺手用」的加信后端；查完发现三条一手文档确认的硬伤（退出码 26.2 前恒为 0、律师开着 LO 时第二个进程只转交参数不干活、CJK 行高的 Word 兼容 26.2 才落地导致中文文书页数系统性偏小），**而本项目用渲染器恰恰就是为了量页数**。它仍然可以留在视野里，但接的时候必须先读 `soffice --version`、必须按产物而非退出码判成败、必须给独立 profile、必须异步起进程加超时 kill。**这个接入成本已经不低于「把现有 Word COM 那条扩到 WPS」，而收益更差。**

### 7.3 对图 #54 中心假设的影响

**没有查出任何动摇它的东西，反而三处加固：**

- mac 侧两格都没有可无人值守的渲染通道，其中主力那一格（mac + WPS）连 API 都没有。**「门禁不能把渲染当前提」这一条被再次坐实。**
- Windows 侧两格能建通道，但**它们量出来的东西彼此不一定一致**（Word 与 WPS 是两套排版引擎，且开发机无方正字体、律师最终从 WPS 打印）。这正好落在「渲染层是机会性**加信**、用来校准第一层」的定位上，而不是「渲染层是真理」。
- 渲染这条路的失败形态比原先设想的更脏（授权挂起、按文件弹窗、GUI 会话依赖、枚举值跨平台不一致）。**一个会以这么多种方式挂掉的东西，不适合做门禁本体。**

## 8. 「需实测」清单（按能不能就地跑掉分三组）

### 8.1 在开发机上就能跑掉的（不用等 Mac）

因为开发机上 Word 与 WPS 都装着（第 4.0 节），这几条随时可测：

1. 32 位 `powershell.exe` 里 `New-Object -ComObject KWPS.Application` 能不能起来（本机是 12.1.0.23542，**不在 12.1.0.22529 / 22525 那个 COM 面失效的版本段里**，见 4.6）；64 位里报的是不是 `0x80040154`。
2. 个人版上**外部** COM 能不能用（金山只说过个人版没有内部 VBA 宏环境，外部 COM 一句话没有，旁证互相打架）。
3. `$app.Visible = $false` 能不能把个人版的首启 / 登录 / 推广窗口一起压住；跑完 `$app.Quit()` 后 `wps.exe` 与那几个守护进程有没有残留。
4. `$app.Name` 是不是真的返回 `"Microsoft Word"`（若是，`Application.Path` 作判据的必要性就坐实了）。
5. 把 WPS 设为默认办公套件、以及跑一次配置工具的「重新注册组件」之后，`HKCR\Word.Application` 有没有被改写（后者是 4.7 那条孤证指名的动作；**两条都要改系统状态，跑之前先想清楚怎么改回来**）。
6. 同一件样例分别用 Word 与 WPS 出 PDF，比 `pdf_checks` 那三项（页数、空白页、行高）差多少。**这一条直接喂给图 #54 的「误差带宽度」问题。**

### 8.2 必须在律师那台 Mac 上才能跑掉的（本轮不可用）

1. `sdef /Applications/Microsoft\ Word.app | grep -c 'format PDF'`，确认现行版本枚举还在（前提是那台机器上装了 Word，而现在没装）。
2. 全新用户下首次 `osascript` 打 Word，一共弹几个窗、分别是什么（TCC Word / TCC System Events / 沙箱文件 / Word 首启）。
3. 文件放 Word 容器内 vs 容器外，`open POSIX file` 是否弹沙箱授权窗。
4. 冷启动到 `save as` 返回的墙钟时间；Word 常驻后第二次的耗时。
5. 多页 + 页脚 PAGE 域的文书，不调 `repaginate` / `compute statistics` 直接 `save as` 出来的页码对不对。

### 8.3 哪台机器上都能跑，但本轮没跑（LibreOffice 未安装）
