# 出一版五段计时（开发机，2026-09-12）

`#123` 的交付物：一条稳定复现的反馈回路，加它量出来的四条事实——**慢在哪一段、多慢、什么规模、是不是每次**。

**只记数与直接推论。优化点不在本文件里**（那是 2 号、3 号票的事）。测量期间没有改过任何一行产品代码。

本文件不含任何案件数据：喂料是 `evals/种子/在办中`（合成工作区，当事人写作甲、乙），路径全在 `%TEMP%` 下。

## 一、反馈回路

六个脚本在 `docs/research/出一版计时/`，标准库零依赖，都可无人值守跑。

| 脚本 | 一条命令看见什么 | 一次多久 |
| --- | --- | --- |
| `分段计时.py` | 段 1/3/4/5 各跑 N 次的 min/中位/max | 约 20 秒 |
| `会话计时.py` | 一次真实 `/loo0ng-doit 出一版` 的全程，模型时间与工具时间切开（Claude Code 侧） | 约 5 分钟 |
| `会话计时codex.py` | 同上，Codex 侧（`codex exec --json`） | 约 3 分钟 |
| `图规模.py` | 段 1 随图规模怎么长（1× 到 16×） | 约 10 秒 |
| `文书规模.py` | 段 3、段 4 随文书规模怎么长 | 约 10 秒 |
| `渲染规模.py` | 段 5 随文书页数怎么长（要 Word） | 约 70 秒 |

两个会话计时脚本靠 `scripts/skill-eval.py --materialize 在办中` 生工作区，跑的是用例「办节点出一版」那一句原话（两版出件加一条律师陈述），所以它们量的是跑得通的全流程，不是一个简化模型。

**切法**：把流里每次工具调用的 `[发起, 回来]` 取区间并集算作工具时间，其余全部算模型。第一版按事件类型逐条归段，漏掉了 Claude Code 侧 93～105 个 `system` 事件的间隙，把模型时间低估了一半；改成取并集之后三轮自洽。

## 二、四条事实

### 慢在哪一段：段 2，别的四段加起来不到 6%

五轮（Claude Code 三轮、Codex 两轮），每一轮都是同一个形状：

| | 总墙钟 | 段 2 模型 | 四段 CLI 合计 | 工具调用次数 |
| --- | --- | --- | --- | --- |
| Claude 第 1 轮 | 357.7 秒 | 约 341 秒（95.3%） | 16.2 秒 | 43 |
| Claude 第 2 轮 | 326.0 秒 | 310.4 秒（**95.2%**） | 15.3 秒 | 36 |
| Claude 第 3 轮 | 260.6 秒 | 245.1 秒（**94.0%**） | 14.7 秒 | 35 |
| Codex 第 1 轮 | 190.2 秒 | 181.5 秒（**95.4%**） | 6.4 秒 | 14 |
| Codex 第 2 轮 | 226.4 秒 | 219.4 秒（**96.9%**） | 6.6 秒 | 18 |

（第 1 轮的段 2 是按总墙钟减工具减启动推的，那一轮跑的是还没改并集切法的脚本。）

### 多慢：单段的数

`分段计时.py`，每段 3 次，单位秒：

| 段 | min | 中位 | max |
| --- | --- | --- | --- |
| （地板）`python` 空进程 | 0.012 | 0.013 | 0.013 |
| （地板）`python -c "import docx"` | 0.070 | 0.070 | 0.071 |
| **段 1** `graph.py views`（只重算） | 0.059 | **0.060** | 0.060 |
| 段 1 `graph.py validate`（只校验） | 0.059 | 0.063 | 0.066 |
| 段 1 `graph.py add-node`（写 + 重算） | 0.056 | 0.057 | 0.057 |
| **段 3** `md2docx.py`（起进程 + `import docx` + 转换） | 0.106 | **0.115** | 0.121 |
| **段 4** `gate.py --no-render`（推算层） | 0.074 | **0.076** | 0.086 |
| **段 5** `gate.py` 全量（推算层 + 渲染层） | 4.159 | **4.522** | 5.684 |

推出来的分解：

- **渲染层本身 = 4.45 秒**（全量减推算层）。
- **`import docx` 本身 = 0.057 秒**；转换本体（起进程与 import 之外的那部分）= **0.045 秒**。

一次出一版里这四段各调几次（实测）：段 1 两次、段 3 两次、段 5 两次。合计约 **9.4 秒**（开发机有 Word 时），其中 8.9 秒是渲染层。

**「每件起一次 Word 的那 7 秒」这个数在本机偏高**：单次全量门禁 4.16～5.68 秒，其中渲染层 4.45 秒。方向不变（渲染层是四段 CLI 里唯一值钱的一块），数要按 4.5 秒记。

### 什么规模：段 1、3、4 在任何现实规模上都是平的

段 1 随图规模（把 `在办中` 的图按倍数复制，并给每个节点塞条目）：

| 模块 | 节点 | `图.json` 字节 | `图视图.md` 字节 | `views` 中位秒 |
| --- | --- | --- | --- | --- |
| 12 | 72 | 17,610 | 13,899 | 0.061 |
| 24 | 144 | 80,225 | 46,735 | 0.069 |
| 48 | 288 | 246,967 | 135,159 | 0.071 |
| 96 | 576 | 666,275 | 357,511 | 0.086 |
| 192 | 1,152 | 2,020,843 | 1,075,743 | **0.150** |

图放大 16 倍（1,152 个节点、2 MB），重算仍只要 0.15 秒。破产领域图本身是 12 模块 72 节点，所以现实规模就是第一行。

段 3、段 4 随文书规模：

| 段落 | 表行 | docx 字节 | `md2docx` 中位秒 | 推算层中位秒 | 门禁结论 |
| --- | --- | --- | --- | --- | --- |
| 1 | 3 | 14,980 | 0.123 | 0.070 | 通过 |
| 10 | 10 | 15,127 | 0.102 | 0.070 | 通过 |
| 40 | 50 | 15,782 | 0.093 | 0.082 | 通过 |
| 150 | 200 | 17,686 | 0.094 | 0.092 | 须目验清单 |
| 500 | 800 | 24,417 | 0.092 | **0.165** | 不通过（页数超阈值） |

500 段加 800 行表（几十页）时推算层 0.165 秒，转换器不长。**这三段没有规模问题，现在没有，翻十倍也没有。**

段 5 随页数（`渲染规模.py`，全量减 `--no-render`，各 3 次取中位）：

| 段落 | 门禁实测页数 | 全量中位秒 | 推算层中位秒 | **渲染层** |
| --- | --- | --- | --- | --- |
| 1 | 1 | 5.537 | 0.081 | **5.455** |
| 20 | 4 | 5.752 | 0.082 | **5.670** |
| 80 | 13 | 4.853 | 0.094 | **4.759** |
| 200 | 30 | 5.491 | 0.092 | **5.399** |

**渲染层与页数无关**：1 页与 30 页同为 4.8～5.7 秒，抖动大于趋势。这一整块是 Word 进程的起停开销，文书本身画多久可以忽略。两批测下来渲染层的区间是 **4.2～5.8 秒**。

### 是不是每次：是

五轮真实会话，段 2 占比 94.0%～96.9%，没有一轮例外。单段计时 3～5 次重复，段 5 的 max/min 比是 1.37，其余各段都在 1.1 以内。段 5 每次都要新起一个 Word 进程再 `Quit`（`gate.py` 的 PowerShell 片段就是这么写的），所以它**恒定是冷的**，没有第二次变快这回事。

## 四、那条线索的答案：`SKILL.md` 最厚不是慢的原因

起手件里那条线索是「`loo0ng-doit` 的 `SKILL.md` 是七件里最厚的（20,450 字节），也正是被报慢的那件」。量出来的是：

- 一次出一版真正压进上下文的盘上内容约 **81 KB**，其中 **46 KB（57%）是 skill 正文加 references**（`loo0ng-doit` 的 20,450 + `loo0ng-to-docx` 的 12,858 + 它的两份 references 12,839），案件材料只有 **860 字节**。
- 但这 46 KB 只在**第一次**进上下文时付 prefill（`cache_creation` 66,670 token 一次），此后 46 次往返读的都是缓存。Claude 第 3 轮从起跑到第一次工具调用只要 9.9 秒，其中还包含 CLI 自身启动。
- 真正乘 46 的是**每次往返的固定成本**，不是正文的字节数。

**所以：正文体量与总时长之间，本轮没有量出因果。** 剪薄正文能省的是一次性的 prefill，省不了那 46 次往返。要缩短出一版，能动的自变量是**往返次数**与**要写多少字**，不是正文有多厚。

这条结论是给 3 号票（正文修剪）与 2 号票（清单该不该动）的输入：**「`loo0ng-doit` 那 20 KB」不能拿「出一版慢」当论据**。要剪它得另找理由（可读性、抖动、维护），不能说是为了快。

## 五、律师那台机上会是什么样

**段 5 在他那边是 0**（ADR-0017、ADR-0018 附注：主力格 mac + WPS 恒定没有渲染后端）。本轮意外拿到了同形状的一格：**Codex 的 `workspace-write` 沙箱里 Word COM 起不来**——

```
NOWORD Retrieving the COM class factory for component with CLSID {000209FF-...} failed
due to the following error: 80070520 A specified logon session does not exist.
```

门禁照常给出「通过」，三项渲染相关判据落到推算区间，只多一条披露项（ADR-0017 的正常路径）。所以 Codex 那两轮的段 5 合计只有 1.0 秒（两次调用，都没起 Word），**这正是律师那台 mac 的形状**。

把渲染层拿掉之后，Codex 侧一次出一版的四段 CLI 合计 **6.4 秒 / 190.2 秒 = 3.4%** 与 **6.6 秒 / 226.4 秒 = 2.9%**。也就是说：**律师那边慢的 96%～97% 是模型，四段 CLI 加起来连 7 秒都不到。**

## 六、跑的是什么机器

| 项 | 值 |
| --- | --- |
| 系统 | Windows 11 Pro 10.0.26200 |
| `python` | 3.14.2（`import docx` 可用，1.2.0） |
| Claude Code 侧 | `claude -p --output-format stream-json`，模型走 CLI 默认 |

| 渲染层 | 有 Word；Codex 沙箱里起不来（见第五节） |

**代价照实记**：本文件是**开发机那一组数**，缺了主力环境那一格。律师那台 mac 上的一次计时由 [#120](https://github.com/f4de01/lawyer-workbench-v3/issues/120) 带回，追加进 #123 的关票评论，不重开票。两组数放在一起才看得出哪一段是本机特有的——但由上面第五节，那一格能带回来的主要是「模型那 95% 在他的机器与网络上具体是多少秒」，五段之间的比例本轮已经在无渲染的那一格（Codex）上量到了。

另有两处本轮没量，照实记：

- **Codex 侧没留逐段的模型时间细账**：它的流把多件事打包进一条 PowerShell 命令（14 次工具调用对 Claude 的 35～43 次），所以第三节那种「写 v1 审查报告花了多少秒」在 Codex 侧切不出来，只有总量。
- **重出到第 2、第 3 次的那条路没量**：本轮两版都一次过门禁，「不通过 → 改稿 → 重转 → 重检」至多 2 次那条支路上的时间没有样本。
