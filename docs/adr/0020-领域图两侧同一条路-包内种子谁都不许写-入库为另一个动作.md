# 领域图的构建两侧同一条路，包内种子谁都不许写，入库是另一个动作

ADR-0019 把领域目录搬出 skill 包，包内 `assets/<领域名>/` 降为出厂种子，并给办案会话开了一条往领域图写的路：律师确认文书之后一句话拍板，agent 经引擎写活图。领域目录取的是工作区 `AGENTS.md` 指针块里那一行绝对路径。

#90 同时裁定 0.1.0 起手的工作区本版不迁移——它们那一行指着包内的出厂种子。两件事各自成立，合起来是个洞：在这样的工作区里走一遍逐节点回流，写的就是随 skill 包分发的那份文件。破的是硬边界 2，但真正的损失在律师那一侧——**那份图下一次包升级就被整个换掉，累计的东西静默消失，而律师这台机器上没有 git、没有隐私钩子，谁都不会知道**。

最先想到的补法是给引擎开一个放行口：律师侧拒，开发侧带一个旗标放行——因为开发者维护出厂种子、跑雏形、批量回流，写的正是那一份。这条补法的前提是"开发侧构建领域图有自己的一条路"。我们把这个前提本身推翻了。

我们决定：

- **领域图的构建，开发侧与律师侧走同一条路。** 开发者要定制或维护一个领域图，就跟律师一样：办一遍，逐节点回流进**自己那份活图**。包内种子不再由任何人"直接写"。收益是 dogfooding——律师那条路上的坑，开发者先踩到；代价是开发者的入场费上升，改一个节点标题从"一条命令加 PR"变成"改活图、入库、PR"。

- **引擎对落在包内的领域图无条件拒，没有放行口。** 既然没有人需要在会话里写包内种子，引擎里就不必有例外分支。判定点在 `Engine.commit()`：**只拦写，不拦读**——`validate`、`views`，以及案件图拿种子当领域图来源（`--domain` 指着它起手、算前方、惰性带入）全部照旧，那是 eval 的回放助手与 0.1.0 工作区每天在走的路。这条规则**只管 `--kind domain`**：案件图落进包内或仓库是硬边界 1 的病，且该在起手那一刻拦，不该在第 37 条条目落盘时才报。

- **判据两条取或，与 `loo0ng-setup-case` 的 `setup.py` 同源**：按脚本自己的位置算出的兄弟 skill `assets/`（装在哪儿都成立），或者目录名摆成 `<…>/loo0ng-domain/assets/<领域名>`（别处拷来的一份包）。两处各留一行互指注释。不加"祖先里有 `.git`"这条判据：它会误伤一个我们希望律师做的事——把 `~/.loo0ng/领域/` 放进 git 做备份。

- **入库是另一个动作，与包发布分开。** 开发者活图那份 `领域图.json` 进仓库成为出厂种子，叫**入库**（`AGENTS.md` 硬边界 2 已经在用这个词，且已经绑定"须经第二双眼"）。它是一次 git 提交、在仓库里做、由第二双眼与隐私钩子把关；ADR-0009 的"维护即发布"说的是另一件事（整个 skill 包的版本发布，changeset + semver），一次包发布可以带零次或多次入库。律师那一侧永远不入库。

- **入库只拿 `领域图.json`，不拿整个领域目录。** 官方模板原件与指引手册原文是原件，进仓库的路本来就是普通的 git 添加，不绕活图走一圈；整份拷会把活图目录下的任何东西卷进仓库，正是硬边界 1 最不想要的形状。`AGENTS.md` 结构不变量第 5 条不受影响。

- **入库经 `sketch.py intake`，回显这次比种子多了/改了哪些节点。** 两侧同一条路带来一个原来没有的风险：开发者的活图里混着他试办案子回流进去的东西，入库从"逐条精挑"变成"整份送进去"，第二双眼要审的 diff 一下子变大且没有摘要。那行"多了 3 个节点、改了 1 个标题"是隐私钩子和第二双眼之前的第一道人眼过滤。子命令不叫 `publish`，避免与包发布混。

- **`sketch.py home` 加 `--empty`。** 开发者要造一份全新领域的种子，起点是"活图位置上什么都没有、包里也没有种子"，`home` 现在拒。两侧同一条路的意思就是开发侧也享受 ADR-0019 那条低入场费，卡在"活图建不出来"这条路就不是同一条。

- **起手那一头不动。** `setup.py` 对 `--domain` 给了包内种子仍然只报不拒：开发侧的种子回放本来就直接对着种子起手（那是读），而洞在写入那一刻已经被堵死——指针记着种子路径的工作区，回流时会被拒并被告知怎么换，损失是"问了一次白问"，不是数据丢失。

- **不新做补历史的机制。** 律师换完指针那一行之后，这个案子里此前已确认的节点不会自动补上（#91 定的是"不写、不再问第二次"）。补它用现成的 `from-case`——它只认 `--domain` 给的那个目录，指活图零改动，缺的只是正文里那一句。

- **落地分三票，顺序是先堵洞再搬家。** 本 ADR 与引擎那条拒同属 #99；`apply` 与 `from-case` 改成写活图（连同 `references/回流.md` 与 `loo0ng-domain` 那张表重画）、`intake` 与 `home --empty` 各一票。中间那段时间开发侧那三条路会撞到拒绝，撞到的人从本 ADR 知道该往哪走——这个顺序换来的是洞一天都不多开着。

## 考虑过的方案

- **引擎开一个 `--seed` 旗标放行开发侧**：一个旗标就够，正文三处各加一个词；但它把"开发侧有自己一条路"固化进引擎，而那条路正是我们要取消的。留着它，两侧的路就永远不会真的合一。
- **靠环境变量、当前工作目录在仓库里、或"祖先里有 `.git`"来认开发会话**：都是环境状态，一个在仓库目录里开的办案会话（开发者拿自己电脑试办一个案子）会静默满足条件，而那正是最该拒的场合。
- **只写进 `loo0ng-doit` 正文，模型自己判**：零成本，但守不住的那一次没有人会知道——律师那台机上没有 git、没有钩子，丢失是静默的。硬边界 1 的守门是机械的（ADR-0014），这一条没有理由更弱。
- **所有写都拒，不分 `--kind`**：让一条规则同时替两条硬边界说话，报错消息就没法写准，而案件图落在包内该在起手那一刻拦。
- **判据加"祖先里有 `.git`"**：覆盖票里那句"或本仓库内"，但会拒掉把活图放进 git 备份的律师。仓库里唯一会被律师侧回流写到的领域图就是包内种子，判据 ① 已经覆盖。
- **起手那一头也从只报不拒改成拒**：要连带改 eval 的回放路径与一条现成单测，换来的只是把一个已经被堵死的洞再堵一次。
- **入库整个领域目录三样**：把活图目录下的任何东西都卷进仓库。
- **eval 那条字节断言直接指仓库里真的 `assets/破产`**：是票里那句话的字面，但那是拿开发者的工作树赌一次规则，规则坏了它会被写脏。改为假包测"拦得住"、单测测"真包在射程里"，两条合起来等价且零副作用。
- **三件后续合成一票**：动四件 skill，第二双眼审不动；`home --empty` 单独成票又只有十几行。

## 后果

- **ADR-0019 部分修改**：它的"开发侧批量回流写出厂种子"改为写活图，出厂种子改由入库更新。加同日附注。
- **ADR-0012 再收一次**：开发侧那条路的终点从种子改成活图，第二双眼的位置从"回流那一刻"挪到"入库那一刻"（本来就是 PR 审 diff，把关强度不变）。加同日附注。
- **`CONTEXT.md` 两处**：「领域图」词条"开发侧批量写出厂种子"改掉；新增「入库」词条。
- **`graph.py`** 多一条拒与一个 `in_package`；`loo0ng-graph` 正文里"出厂种子只在开发会话里改"改掉；`loo0ng-doit` 正文补一句被拒之后怎么跟律师说。
- **后续两票**：`apply`/`from-case` 搬家；`intake` 与 `home --empty`。
- **一条代价照实记**：开发者维护种子多一步。换来的是引擎零放行口，以及两侧同一条路。
- 本 ADR 满足三条件：两侧同一条路一旦落地，后续几票的正文、测试与开发流程都建在它上面，回头要重新造一条开发侧专用路；"引擎连开发者都拒"没有上下文会让人以为是漏了放行口；每一条都在两三个方案之间选过。
