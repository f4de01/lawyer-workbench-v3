# 以数据层保护替代逐项确认

2.0 把律师的四项发起权（批准、节点标记、分支适用、律师陈述）做成两段式脚本：先出示、再落盘，每个动作律师都要确认两次；同时六条原则里又写着"自动优先、不做前置逐项确认"。两条互相抵消，试用结论是"反复确认"（handoff §2.1）。legal-skills 走了另一条路：状态文件里每一行带 `source: user|ai`，AI 永不覆写律师写的行，保护落在写入代码里而不是提示词里，于是 AI 可以放手写、不必每步问。

我们决定：3.0 用数据层保护替代对话确认。律师的动作只有两个（确认、不适用），在对话里说一句、agent 落盘一条并回显，没有出示与落盘两段。保护有两条：图里律师的条目带来源标记，agent 永不改动，写入引擎代码级拒写；agent 永不写入案件工作区里已存在的文书文件，每次生成都是新版本，律师在 Word 里改过的文件天然不会被碰。图本身就是案件唯一的台账，2.0 的节点标记、批准记录、分支适用、版本记录、取值台账五张表不再存在；律师只读由图派生的视图。

借鉴的是 legal-skills 的结构（单一状态文件、单一写入引擎、行级来源保护、派生视图自动刷新、业务键行身份），不借它的代码：`fcntl.flock` 在 Windows 不可用，近三千行核心代码零测试，16 节 schema 是诉讼语义。若实测证明其结构好用，可参考结构自建。设计上必须保证不冗余：一个事实只在一处存，其余皆派生。

## 考虑过的方案

- 沿用 2.0 两段式，只减少动作数：确认次数仍随文书数线性增长，律师在 2.0 试用里明确不接受。
- 完全不保护，靠提示词约束 agent 不改律师内容：legal-skills 的教训是保护必须在代码层，提示词级约束在长会话里不可靠。
- 文书内部区域级保护（agent 只改自己写的段落）：需要 docx 段落级归属追踪，本机没有 LibreOffice，Windows 上没有可靠工具；等真实案件出现"改了一半要 agent 续"再议。

## 后果

- 律师主循环里没有确认对话框；律师改主意就再说一句、再落一条，旧条目留在历史里。
- 图的存放格式与写权票必须在"单一文件 + 写入引擎 + 代码级拒写 + Windows 锁 + 派生视图"这个前提下做，不得回到多张登记表。
- 文书出件机制票必须让每次生成都同时产出文书与审查报告两个新文件，并以直接可提交为目标。
- 2.0 案件工作区里的五张表在迁移时并入图，取值台账废弃，裁定台账并入律师陈述。
