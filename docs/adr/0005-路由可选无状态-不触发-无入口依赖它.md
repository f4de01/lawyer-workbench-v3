# 路由可选、无状态、不触发，没有任何入口依赖它

路由是律师随时可问的只读地图，回答「当前节点、上一完成、下一任务」三问并指出下一句该打什么。做路由的定位机制时，有一条把它写成主入口的诱惑：每个动作都先经路由，路由把参数填好递给下一个 skill，或者在图里记下"上次路由指到哪"。我们决定相反：

- **路由是 standalone，永远不是链上的一步**。与 ask-matt 一样，它只指出这一个对话的方向；不用、每轮用、偶尔用，案件都走得一样。没有任何编排入口依赖路由被调用过，前置只是"案件图存在"。
- **路由无状态**。它的回答不成为图里的状态，图仍是唯一事实来源（ADR-0003）；每次回答完整、不接上一次。
- **路由不触发、不替人按下去**。它只给出一行"入口名 + 一句自由文本"，由律师自己打。这一行在 Claude Code 是 `/名 …`、在 Codex 是 `$名 …`，整串原样给对方；对方入口自己读案件图，路由不替它打包上下文。
- **路由自持入口表，不读目录**。编排入口对模型是藏起来的，SKILL.md 两平台共用，所以路由自己维护一张入口表，只指向表里真存在的入口。

## 考虑过的方案

- 路由作为主入口、参数由它填好递给下一个 skill：Claude Code 对用户调用的 skill 硬拦，Codex 的 skill 没有参数机制，两边都没有"排队给下一会话"的机制；能递的只有自由文本，而那正是律师自己能打的。
- 路由在图里记"上次指到哪"：让一个只读者写图，破坏单写者与"状态只算不存"，且多案件、多对话下立刻失真。
- 在 SKILL.md 里用 `!`ls`` 读真实 skill 目录以免"报未安装"：Claude Code 独有，Codex 里是普通文本。

## 后果

- 每个编排入口都必须能在没有路由的情况下独立被打，并接受整串自由文本（动作 + 节点 + 补充）。入口名只能 `a-z 0-9 -`，中文进显示名。
- 入口分开还是合并只改路由的表，不改路由的回复形状。改任何入口须同步改表；这条维护规则的落点按 `AGENTS.md` 元规则等第一次真实违反再写入。
- 「下一任务从领域图里挑哪一个」等定位规则不在本 ADR 里，见票「路由的定位机制」与分支 `prototype/路由定位` 的原型。
