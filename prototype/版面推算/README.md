回答 issue #55（地图 #54）：**能不能不靠渲染器，只读 DOCX 就算出门禁那三项渲染相关的判据？**

**不要合进 main。** 结论进 ADR，代码要重写才进 `skills/loo0ng-to-docx/`。

## 跑

```
python prototype/版面推算/推算.py <文书.docx>            # 只推算，无依赖
python prototype/版面推算/对照.py --json 对照结果.json    # 与 Word 真渲逐件比对，要 Word，约 4 分钟
```

## 两个文件

- `推算.py` —— 推算器。**只 import zipfile 与 xml.etree（标准库）**，无第三方依赖，python 3.9 兼容。
- `对照.py` —— 比对台。直接 `import gate` 用它的 `render_pdf` 与同样的 PyMuPDF 调用取真值，保证比的是同一把尺子量出来的数。**这个文件是原型专用**，正式实现里推算器不会 import 门禁。

## 原理

官方模板里页面几何、列宽、字号全是死数，而 **CJK 全角字符的 advance 恰好等于字号**（`w:sz` 是半磅，故 advance = `sz/2` 磅 = `sz×10` twips）。于是「一格几行」是算术，不需要字体度量、不需要字体文件——**也因此不受字体替换影响**。

输出是区间 `[下界, 上界]`，两组参数各跑一遍：

| | 西文宽度 | 行高系数 | 禁则 |
| --- | --- | --- | --- |
| 下界 | 0.5 em | 1.15 | 不计 |
| 上界 | 1.0 em | 1.35 | 每个折行段落多算一行 |

行高再加量测容差 `×0.98 ~ ×1.02 + 2 磅`：PyMuPDF 的 `row.bbox` 含横线本身，渲染还有取整。

## 一个必须建模的坑：纵向合并

`vMerge` 续格与上一行之间没有横线，渲染出来是一条双高的带，PyMuPDF 的 `find_tables` 也就把它们读成**一行**。所以推算要把被 `vMerge` 连起来的相邻行并成「带」，带高 = 成员行高之和。

不建模时，四件含合并单元格的模板（`1-1`/`3-1`/`3-2`/`8-2`）行高低估 34%～51%（低估是危险方向）；建模后全部落进区间，误差 ≤2%。

**顺带一条关于现行门禁的事实**：它的行高判据在这四件模板上量的本来就是「合并带」而不是「行」。不是错，但与「行高」这个名字不是同一个量。

## 结论（详见 #55 的 resolution 评论）

25 件样本（19 件官方模板占位件 + 4 件 fixture + 2 件故障件）：

| 判据 | 实测落在推算区间内 |
| --- | --- |
| 页数 | 25/25 |
| 空白页 | 25/25（含故障件的第 2 页） |
| 最大行高 | 25/25 |

**零翻转**：没有一件「推算给出确定结论、而实测结论相反」。
另跑一次贴页边扫描（14～32 段，10 个点），实测页数全部落在区间内，区间宽度稳定 ±1 页。
